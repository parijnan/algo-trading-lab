Gate: trade-for-trade agreement with the production-parity backtest (`helios_backtest/parity_backtest_helios.py`), via the fake Hestia over the real GOLDPETAL 1-minute data. `helios_backtest/helios_configs.py` is the source of truth for every parameter; read fresh, not from this file or memory. ## 1. What Helios is, and how it differs from Selene

Decided config (`helios_configs.py`, confirmed 2026-09-29, plan §4g): GOLDPETAL, ST period 10, **multiplier 3.5**, **stop-loss 1.6% of entry, no targets** — walk-forward validated, not the naive full-window pick. A single position, no scale-out — but **1 unit = 20 lots**, not Selene's 1. The only exits are the stop and the opposite trend flip (plus the roll machinery). Decision *logic* is identical to Selene's; the only real difference is the lot-count scaling:

| | Selene | Helios |
|---|---|---|
| Position shape | 1 lot, no targets | 1 lot-**group** (20 lots), no targets |
| `lots_per_unit` | 1 | **20** (user's own instinct, raised mid-Phase-3: GOLDPETAL's 1-gram lot is too small to be one unit) |
| Margin arithmetic | LTP × lot size / 8 × 4 | LTP × lot size / 1 × 0.0927 (per LOT) × 20 (`lots_per_unit`, an explicit factor — see §2) |
| Rollover buffer before close | 14 min (same as Selene, not Prometheus's 15) | 14 min, unchanged |
| Roll window | 5 trading days | 5 trading days (GOLDPETAL's own tender period, independently user-confirmed 2026-09-29, plan §2 — not just carried over) |
| Sizing | paper, static units, on hold | **paper, static units, on hold** — same posture; position sizing and risk of ruin are explicitly deferred (user, 2026-09-29: "We'll get to position sizing and risk of ruin later") |

Everything else — `hestia_core.roll_policy`'s functions, the request-per-decision discipline, ledger-wins reconciliation, retry policy, the post-close guard — is shared verbatim with Selene and Prometheus, untouched.

## 2. The one genuine engineering question: `lots_per_unit`

Selene's engine (`selene_engine/engine.py`) hardcodes `lots = units` in every order-sizing call site, because Selene's own unit *is* 1 lot — there was never a reason to generalize it. Porting for Helios's 20-lot unit meant finding every such site and scaling it, not just swapping config values:

- **`engine.py`, four sites**: `_send_entry`'s `lots = units` → `lots = units * self.cfg.lots_per_unit`; `_start_flip`'s `new_lots = units if allowed else 0` → `new_lots = units * self.cfg.lots_per_unit if allowed else 0`; `_coincident_flip_transition`'s `lots = units` → the same scaling; `_reconcile_with_ledger`'s adopt-an-unexpected-position branch, `units = max(1, lots)` → `units = max(1, lots // self.cfg.lots_per_unit)` (divides back down instead of wildly overstating units on an unexpected broker position — a 40-lot surprise position is 2 units, not 40).
- **`levels.py`**: `margin_per_unit()` gained an explicit `× cfg.lots_per_unit` factor. This deliberately does **not** match Prometheus's own pattern (`prometheus_engine/levels.py`'s margin formula has no `lots_per_leg` factor at all) — Prometheus's divisor/multiplier were calibrated directly against a real observed *per-unit* (2-lot) margin figure, absorbing the lot count implicitly. Helios's own figure (LTP 14,893, margin ≈1,380, plan §2) was reported for **one lot** — the natural quantity a broker screen quotes — so the config stays directly checkable against a live 1-lot margin quote, and `lots_per_unit` is a separate, explicit multiplier. Documented in both files' own docstrings so the deviation from Prometheus's shape isn't mistaken for an oversight.
- **`hestia_config.py`'s own `EngineEntry.lots_per_unit`** (used by `hestia_core.core`'s admission/cap check, `cap_lots = unit_cap × lots_per_unit`) is a **separate** declaration from the engine's own config field — both need the same value (20) but live in different places and are set independently. Confirmed by reading `core.py` directly: this field is a cap/validation input, not something that auto-multiplies whatever lot count the engine requests — the engine must still compute and request the correct lot count itself.

**A real bug this uncovered, caught by mutation-testing before it shipped**: a first cut of the "does the live margin check actually use the ×20 figure" test used a cash value chosen to sit just under the correctly-scaled requirement — but that value was *also* insufficient under a mutated (missing ×20) version, and separately, Hestia's own **independent** host-level margin gate (`hestia_core/core.py`'s `_entry_limits`, its own `_margin_per_lot` calculation, unrelated to the engine's `levels.margin_per_unit()`) rejected the order first regardless of what the engine's own pre-check concluded — so the "live" test could never distinguish the mutation no matter what cash value was chosen. Removed rather than forced; the engine's own margin formula is precisely covered by a direct unit test instead (§3).

## 3. Verification

Same two-tier method as P7 (`plans/hestia-p7-selene-engine.md` §2), and the same posture: Helios has never traded, live or paper, so nothing here touches Delos or the broker until deployment (§5).

**Engine unit tests and fake-Hestia scenarios.** `tests/helios_engine_helpers.py` (ported from `selene_engine_helpers.py`), `tests/test_helios_engine.py`, `tests/test_helios_engine_ports.py`, `tests/test_helios_engine_roll.py` — near-verbatim ports of Selene's own three files, with `CFG` overriding `lots_per_unit` to 1 so every ported numeric assertion (lot counts, fill sizes) carries over unchanged from Selene's own proven values; the real 20-lot scaling gets its own dedicated file instead of being threaded through every scenario. Two real porting bugs found and fixed while running these (not just renamed): (1) three assertions in the roll tests hardcoded Selene's own 3.0% stop as a literal `1.03`/`0.03` factor — a plain sed rename can't catch a numeric literal tied to the wrong instrument's config, since it isn't a name; fixed to reference `CFG.sl_pct` directly. (2) `test_dynamic_sizing_uses_the_live_margin_and_never_returns_less_than_one_unit` assumed the raw (uncapped) unit computation would land under Selene's own `unit_cap=50` the way Selene's much larger effective margin multiplier happened to keep it — Helios's own much smaller multiplier means the raw figure actually exceeds the cap, so the test's own expected value needed `min(..., unit_cap)`, not just the raw division.

`tests/test_helios_engine_lots_per_unit.py` (new, no Selene equivalent): the real 20-lot-per-unit scaling exercised end to end — entry requests 20 lots for 1 unit, a Rule 7 flip requests 20 on the new side, a coincident-flip re-entry requests 20, an unexpected 40-lot broker position is adopted as 2 units (and a non-multiple 25-lot surprise floors to 1 unit rather than 25), and `margin_per_unit()`'s value is exactly 20× the per-lot figure.

**Whole suite, four files: 63 passed** (58 ported/adjusted from Selene's own three files, matching its own 54-plus-growth, plus 1 new direct margin-scaling unit test in `test_helios_engine.py`, plus 5 new in `test_helios_engine_lots_per_unit.py`; final count after both porting bugs above were fixed and the flawed "live" margin test removed).

**Mutation checks, five mutations targeting every `lots_per_unit` site, all killed**: the entry-lots scaling, the flip-lots scaling, and the coincident-flip-lots scaling each reverted to Selene's bare `lots = units`, all caught immediately by the corresponding dedicated test. The ledger-adopt reverse-division reverted to `units = max(1, lots)` — caught by both the 40-lot and the 25-lot (non-multiple) test. The `margin_per_unit()` ×20 factor removed — caught by the direct unit test in `test_helios_engine.py`; the attempted "live" end-to-end version of the same check could not distinguish the mutation at all (§2) and was removed rather than kept as false coverage.

## 4. Parity-backtest replay (P8.2)

Done. `helios_engine/replay_check.py` (`python -m helios_engine.replay_check [end_date]`, ported from `selene_engine/replay_check.py` with `FREEZE_QTY_LOTS` corrected to GOLDPETAL's own 10,000 — Selene's SILVERMIC was 600 — `lots_per_unit` corrected to `DEFAULT.lots_per_unit`, and the carried-position seed helper's hardcoded `units=1, lots=1` generalized to `lots=DEFAULT.lots_per_unit`) drives the engine on the fake Hestia over real GOLDPETAL 1-minute data and compares its trades to `helios_backtest/data_sweep/parity_trades.csv`/`parity_legs.csv` leg for leg. `tests/test_helios_engine_replay.py` pins the result.

**Scope.** Same reasoning as Selene's own P7.2 (`plans/hestia-p7-selene-engine.md` §4): the parity backtest's `load_contracts` blends Fyers (preferred) and AngelOne; Hestia's live data path is AngelOne-only. The two sources coincide only from `helios_configs.ANGELONE_OWN_FROM = '2026-09-02'` onward. Replay window: `[2026-09-02, 2026-09-25]` (`helios_configs.PARITY_END_EXTENDED`).

**Result: 24 of 24 live decisions reproduced, zero fill-price gap** (both simulations read the same 1-minute data, so a fill is identical to the cent), and exactly three differences, all root-caused as structural artifacts of how "live decisions" are built from `parity_trades.csv`, not engine bugs — verified directly against `parity_trades.csv`/`parity_legs.csv`, not assumed:

- **A rollover exit + reopen pair at 2026-09-23 23:16.** Trade 1128 has two legs; leg 2 opens on the new contract (2026-10-30) at 2026-09-23 23:15 mid-trade. "Live decisions" are built from `parity_trades.csv`'s overall per-trade entry/exit only (never from `parity_legs.csv`'s individual leg entries), so an intermediate rollover leg never appears as its own live decision even though the replay engine correctly performs it — the same category as Selene's own excluded `forced_roll` artifact, a different specific cause (Helios's rolls monthly, giving far more chances for this shape of boundary case than Selene's quarterly cadence ever produced).
- **An entry at 2026-09-25 19:00.** Opens trade 1130, still open when the backtest's own simulation window ends (`PARITY_END_EXTENDED`) — `parity_trades.csv` only records closed trades, so this entry has no live counterpart, the same category as Selene's own excluded "still open at window end" case.

**Verification.** `tests/test_helios_engine_replay.py` (1 test, skips itself when the pipeline GOLDPETAL data or the backtest's `data_sweep` output is absent): asserts every live decision matches except the three named, explained boundary cases, and that fill prices agree to the cent.
