# Hestia P7: the Selene engine

**Status: started 2026-09-29.** Phase P7 of `plans/selene-production.md` §10. Gate: trade-for-trade agreement with the parity backtest (`selene_backtest/parity_backtest_selene.py`), via the fake Hestia over the real SILVERMIC 1-minute data. Independent of P6 (Prometheus's cutover): Selene has never traded, live or paper, so nothing here touches Delos or the broker. `selene_backtest/selene_configs.py` is the source of truth for every parameter; read fresh, not from this file or memory.

## 1. What Selene is, and how it differs from Prometheus

Decided config (`selene_configs.py`, confirmed 2026-09-25): SILVERMIC, ST period 10, **multiplier 2.5**, **stop-loss 3.0% of entry, no targets**. A single position, no 2-lot scale-out (`LOTS = 1`). The only exits are the stop and the opposite trend flip (plus the roll machinery). This is materially simpler than Prometheus:

| | Prometheus | Selene |
|---|---|---|
| Position shape | 2 lots, lot1 books at target1, lot2 rides to target2 | 1 lot, no targets |
| Exit reasons | `stop_loss`, `target1`, `target2_*`, `trend_flip`, `roll`, `manual_exit` | `stop_loss`, `trend_flip`, `roll`, `manual_exit` |
| Rule 7 flip | one netted `FlipRequest` (close 2, open 2) | one netted `FlipRequest` (close 1, open 1) — same request kind, no lot-order subtlety |
| Provisional-boundary trading | yes (previous-ST margin guard) | **not modelled by the parity backtest; not built here** (open point, section 6) |
| `lots_per_unit` | 2 | 1 |
| Margin arithmetic | LTP × lot size / 3 × 4 | LTP × lot size / 8 × 4 (`MARGIN_CONTRACT_VALUE_DIVISOR`/`MARGIN_SIZING_MULTIPLIER`) |
| Rollover buffer before close | 15 min | **14 min** (`ROLLOVER_BUFFER_MIN`) — passed to `roll_policy.rollover_time`'s `before_close_min`, not the default |
| Sizing | live, static units | **paper, static units — sizing is ON HOLD pending the user's review** (`project_selene.md`); the engine supports dynamic sizing generically (same arithmetic shape) but nothing chooses a live figure here |

Everything else — roll rules, request-per-decision discipline, ledger-wins reconciliation, the request-pending state, retry policy — is `hestia_core`'s and `roll_policy`'s, shared verbatim with Prometheus. `hestia_core.roll_policy`'s functions (`effective_from_days_left`, `arm_action`, `rollover_time`, `basis_price`, `reopen_plan`, `decide_rollover`, `coincident_flip`, `restart_action`) are called directly, parameterised by Selene's own `roll_window_days` (5, same as Prometheus) and `rollover_buffer_min` (14).

**Not ported from the parity backtest**, because it is a backtest-only artifact, not a live behaviour: the "forced roll" path (the held contract silently stops matching the resolved front contract mid-run, because the spliced historical data has a gap or a not-yet-tracked contract) is a workaround for missing historical rows, never a real production situation — a live effective contract does not change intraday. Not built.

## 2. Verification plan

Two tiers, mirroring P5's method (`plans/hestia-p5-prometheus-engine.md` §2), adapted because Selene has no live trading history to replay against:

- **Engine unit tests and fake-Hestia scenarios** (this slice, P7.1): entry, stop, trend flip, Rule 7 as one netted request, restart resume, partial fill, failed/unconfirmed requests, the ledger-wins reconciliation, roll flows (flat-switch, in-trade arm, fallback carry with the 14-minute buffer and the historical basis, veto, coincident flip, no-next-contract flatten), the missed-flip startup reconcile, the post-close guard (ported straight from Prometheus's P5.4 finding — the same bug class applies here). Config and level-formula parity against `selene_configs.py` pinned by a test, same discipline as Prometheus's AST-extraction test.
- **Parity-backtest replay** (P7.2, next slice): drive the engine on the fake Hestia over the real SILVERMIC 1-minute data (`data_pipeline/data/mcx/SILVERMIC/`) with `hestia_core.replay.ReplayData` computing bars and ST the normal way (no logged-bar oracle exists here, unlike Prometheus's recorded live days — the oracle is the backtest's own deterministic `parity_trades.csv`/`parity_legs.csv`), and compare the engine's trades to it leg for leg: entry time, direction, exit time, reason, P&L points. Exact agreement is the gate; any difference is either a backtest limitation already documented (§13 caveats) or a real divergence to fix.

## 3. P7.1 record (2026-09-29): `selene_engine/`

Done. `selene_engine/` (`engine.py`, `engine_configs.py`, `levels.py`, `state.py`) is Selene's decision layer against `EngineContext`, structurally a trimmed copy of `prometheus_engine/` (same request-per-decision discipline, ledger-wins reconciliation, retry policy, post-close guard) with the 2-lot/target machinery removed. `hestia_config.ENGINES['selene']` already names the factory (`selene_engine.engine:build`, `lots_per_unit=1`, `paper=True`); it stays disabled (sizing is on hold, `project_selene.md`).

**Position shape.** A single lot, no scale-out, no targets (`selene_configs.py`: `DECIDED_MULTIPLIER=2.5`, `DECIDED_SL_PCT=3.0`). Exit reasons are `stop_loss`, `trend_flip`, `rollover`, `slack_exit` — no `target1`/`target2_*`. The shared trade-record format (`hestia_core.interface.TRADE_RECORD_COLUMNS`, enforced by `HestiaCore.report_trade` for every engine, found while smoke-testing the first entry) maps Selene's single lot onto Prometheus's `lot1_*`/`total_pnl_*` fields, `lot2_*` left blank — the same shape Prometheus itself uses when its own lot 2 never opens.

**Selene's own rollover buffer.** `selene_configs.ROLLOVER_BUFFER_MIN = 14`, not Prometheus's 15. `SessionStart.rollover_time` carries Hestia's own default (`CoreConfig.rollover_time = time(23, 15)`, or a fixed `23:40` on a 23:55 close) — both are exactly 15 minutes before MCX's only two real closing times (23:30 and 23:55, `mcx_market.closing_time_str`), so the engine recovers the session close by adding 15 back and reapplies its own 14-minute buffer (`_own_rollover_time`). Verified in a fake-Hestia scenario (`23:16`, not Prometheus's `23:15`) and pinned by a test.

**Not ported**, because the parity backtest does not model it and nothing calibrated it: provisional-boundary trading. `DataSpec(provisional=ProvisionalSpec(False))`. The parity backtest's "forced roll" path (a mid-session contract-resolution change caused by a gap in the spliced historical data) is a backtest data-completeness workaround, not a live behaviour — a live effective contract never changes intraday — and is not built.

**Verification.** `tests/test_selene_engine.py` (24), `tests/test_selene_engine_roll.py` (13), `tests/test_selene_engine_ports.py` (17), on the fake Hestia over scripted price paths (`tests/selene_engine_helpers.py`, a trim of `prometheus_engine_helpers.py`). Config and stop-level parity against `selene_configs.py`'s decided values and the parity backtest's own `sl = ref * (1 - sign * sl_frac)` arithmetic, pinned by AST extraction and a direct formula check. Scenarios: entry, the trend-flip exit and re-arming, levels off the real fill, Rule 7 as one netted request with the old trade booked at the flip's fill (and a stub-context check that a flip signal never overlaps an outstanding request), the stop, a stale price never triggering it, a partial entry, a failed entry, a failed exit retried until it lands, EXIT (with and without a position), margin refusal, an engine crash and resume without a second entry, the ledger-wins cases both ways, the entry and exit timing guards, the post-close guard (ported straight from Prometheus's P5.4 finding, both as a fake-Hestia scenario and a direct unit test), the missed-flip reconcile (baseline, entry, deferral and retry, drop when the state moved on, Rule 7, exit-only inside the guard, agreeing flip, no flip, multi-day coalescing), sizing and the affordability check, and roll flows (own 14-minute buffer, flat-eve switch, fallback carry with the basis recalibration, veto, no next contract, coincident flip, exit-only flip, missed roll in both directions including a rejected retry, catch-up, a rejected fallback close and a rejected coincident close each retried). Whole three-file suite: 54 passed.

**Mutation checks** (nine mutations, all killed on the second pass): the state replaced instead of reset in place, the stop comparison inverted, stale prices accepted, ledger reconciliation removed, the reopen outcome switching contracts with the old position open, and Selene's own 14-minute rollover buffer silently reverting to Prometheus's 15 were killed on the first pass. Three survived that pass — the flip-overlap guard removed, the close guard removed, the missed-roll retry removed — because the mutation script only ran `test_selene_engine.py` and `test_selene_engine_roll.py`, leaving out `test_selene_engine_ports.py`, which already held (or, for the flip-overlap and missed-roll cases, was missing and got added) the direct unit test for each. Rerun with all three files: all nine killed.

## 4. P7.2 (next slice): parity-backtest replay

Not started. `selene_backtest/data_sweep/parity_trades.csv`/`parity_legs.csv` already exist (to 2026-09-23) — no new backtest run needed, just the replay and comparison.

**A scoping point found while planning this slice, before any code is written.** The parity backtest's `load_contracts` (`parity_backtest_selene.py`) blends Fyers (preferred) and AngelOne (`data_pipeline/data/mcx/SILVERMIC/`, `ANGELONE_DATA_DIR`) per `selene_configs.ANGELONE_OWN_FROM = '2026-09-02'` and the Fyers-void backfill rules (`selene_data_loader.py`'s docstring). Hestia's own live data path (`ContractCatalog`/`hestia_core.replay.ReplayData`) reads only `data_pipeline/data/mcx/SILVERMIC/` — AngelOne, no Fyers. So an exact leg-for-leg replay is only meaningful **from 2026-09-02 onward** (`selene_configs.ANGELONE_OWN_FROM`), where the two sources coincide; older trades used data the live engine will never see, and are not a fair comparison. Scope P7.2's replay window to `[ANGELONE_OWN_FROM, PARITY_END_EXTENDED]` and say so in the record, rather than attempting (and failing to explain) full-history agreement.

Drive the engine on the fake Hestia over that window with `hestia_core.replay.ReplayData` computing bars and ST the normal way, and compare the engine's trades to the parity CSVs leg for leg. Unlike Prometheus's P5.4 (live logs as the oracle), the oracle here is the backtest's own deterministic simulation — exact agreement is the gate over the scoped window, and any difference is either a backtest limitation already documented (`parity_backtest_selene.py`'s docstring, "not modelled") or a real divergence to fix.
