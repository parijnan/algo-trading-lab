# hestia_core

Hestia is the MCX multi-strategy host: one process, one Angel One login, several strategy engines (Prometheus, Selene, Helios, later Typhon) running side by side. Engines decide (entries, exits, stops, the roll); Hestia does the work (orders, fills, retries, reconciliation, data, alerts, teardown). Plans and decisions: `plans/selene-production.md` (design), `plans/hestia-interface-spec.md` (the engine interface, v1.1), `plans/hestia-p1-inventory.md`, `plans/hestia-p4-live-services.md` (this build).

**Status:** built and tested against doubles, and **live on Delos since 2026-09-29** (Prometheus, 1 unit, cap 10, `plans/hestia-p6-cutover.md`), with **Selene and Helios running alongside it, both paper, 1 unit, cap 10** (`plans/hestia-p7-selene-engine.md`, `plans/hestia-p8-helios-engine.md`). `hestia_config.ENGINES` itself has nothing enabled; which machine may trade is a hostname lookup (`hestia_config.TRADING_HOSTS`, or a gitignored per-machine `hestia_local.py` on top of it) — see "Which machine may trade" below — so `hestia.py` on any other machine (the laptop) still exits before it logs in, and cannot evict another process's session.

## How it fits together

```
engines (engine threads)                                    the interface: interface.py (frozen dataclasses, two Protocols)
   |  ctx.next_event / ctx.submit / ctx.position ...
HestiaCore (core.py)  policy, once: request registry, admission, priority dispatch, ledger, UNCONFIRMED reconciliation, supervision
   |  three ports (ports.py)
   +-- Scheduler   SimKernel (fake_kernel.py) | RealReactor (reactor.py)
   +-- BrokerPort  SimBroker (replay.py)      | AngelBrokerPort (angel_broker.py) via BrokerGateway (gateway.py); PaperBroker; BrokerRouter picks per engine
   +-- DataPort    ReplayData (replay.py)     | LiveData (live_data.py) over mcx_market.py, history.py, candle_fetch.py, feed_port.py
roll rules for every engine: roll_policy.py (pure functions, pinned to Prometheus's contract resolution and basis lookup)
recorded live days as an oracle and replay input: recorded.py (log parser, trades cross-check, data-path table, LoggedReplayData; `python -m hestia_core.recorded`)
cutover aids: preflight.py (`python hestia.py --check`: no-login start report), slack_bridge.py (where the Slack listener writes Prometheus's flags and sizing, standalone or hosted), ../prometheus_engine/seed_state.py (standalone state to the engine's state); plan plans/hestia-p6-cutover.md
host: host.py (HestiaHost) + lifecycle.py (teardown order, signals) + flags.py + state_store.py + sizing.py + session_lock.py
      + slack_queue.py + alert_router.py + reporting.py; entry point ../hestia.py, configuration ../hestia_config.py
```

The fake Hestia (`fake.py`) and the live one are the same `HestiaCore` on different ports, so the contract tests (`tests/test_hestia_fake_*.py`) exercise the policy that trades. Live pieces have their own tests against scripted doubles (`tests/smartapi_double.py`).

## Guarantees engines can rely on

- One request per decision; Hestia owns retries, partial-fill completion of exits, ghost-order recovery and fill confirmation. Request ids are idempotent, also across a process restart (the request journal).
- An engine changes its state only on a confirmed outcome (`FILLED` / `PARTIAL`). `UNCONFIRMED` is settled by reading that order's own broker row; an order still working at the broker is never reported as "no fill".
- Priority when engines clash: stop or flatten, then closes, then roll exits, then entries, then roll re-opens; entries can hold only part of the execution workers so a stop never queues behind them; requests of one engine on one contract are served in submit order.
- Hard limits at admission that engine bugs cannot bypass: the unit cap (only ever from configuration), no entry inside the roll window (5 trading days to expiry), no request at or after the session close, margin reserved against the engine's own pool (the live account, or a paper engine's own cash).
- Crash containment: an engine that raises is resumed from its saved state with backoff and a retry limit, never touching the session or other engines. A silent engine raises Slack alerts. `KILL` stops one engine and leaves its position untouched.
- Shutdown order: stop engines, wait for their threads, let in-flight requests finish, flush Slack, `terminateSession` once, only if every engine thread finished.
- Provisional bars (engines opt in through `DataSpec.provisional`): at a 15-minute boundary whose candle window holds fewer than 15 candles Hestia sends a `ProvisionalBar` built from the websocket ticks, then the real bar later (flagged as reconciling it). Note the window is also short whenever a minute had no trade (Angel One omits untraded minutes), so on thin contracts this fires on quiet minutes, not only on AB1021 failures. The engine decides whether to act. All four engines have the handling, **on** from 2026-10-08 (`provisional_enabled`), each with a margin set from history (the mean final-minute range per instrument: Selene 0.05%, Helios 0.04%, Typhon 0.11%, Prometheus 0.07%), a shadow mode that logs without acting (`provisional_shadow`, effective only when enabled is False), and, in the three newer engines, a gate that skips the action while the feed is stale: `plans/hestia-provisional-all-engines.md`. The provisional bar is built only after the poll's whole fetch job, which includes the Angel One retries and the Fyers rescue, so it is the net below them. Hestia itself does not check feed freshness before building the provisional bar; the engine does.

**Live archive and the seed (2026-10-27).** The minutes the engines' Supertrend is built from during a session are the intraday cache's rows (Fyers-first, Angel One for any window Fyers could not serve). Until 27 Oct the first read of the next day deleted them and the 09:00 seed rebuilt the past from the pipeline file instead, which is a separate Angel One download: on 26 Oct 2026 that file's NATGASMINI minutes had spikes the live feed never had (about 50 highs and 60 closes differing from Zerodha's chart on that one day), the rebuilt band was 293.73 against the live 292.40, and Typhon seeded bearish while holding a live bullish position. Now `TodayCache.roll_over` moves the older rows to `cache/<token>_live_1m.csv` (kept 30 days; the archive is written first, and a failed write leaves the intraday file unpruned), the seed calls it before reading the past, and `LiveData._prefer_live_archive` takes a past day from the archive when its 15-minute buckets run unbroken from the session open to the last bucket before the close; any other day (a crash, an early stop, a gap, a day before the archive began) comes from the pipeline file as before. The seed logs which source each day used (`seed <symbol> history: N day(s) from the live archive [...], M from the pipeline [...]`). The minutes between the cache's last row and now at a restart (`LiveData._seed_gap`) are fetched Fyers first for the Fyers-first instruments with the Angel One burst behind it, the same order as the live poll (before 2026-10-27 that gap was Angel One only). Not exact in one case: the disk cache keeps the first copy of a minute while the in-memory series keeps the last, so a minute Angel One's 5-minute fallback window re-delivered can differ between the two (4 of 3,476 windows on 26 Oct); Fyers-first windows return only minutes not already held and are unaffected.

**Trend guard (`hestia_core/trend_guard.py`, 2026-10-27, all four engines, alerts only).** The ledger and broker-book reconciliations compare positions, never a position with the trend, so a wrong seed could leave an engine long in a bearish series with every check green. Two alerts close that, both critical, neither changes a decision: (1) every bar the engine processes stores the trading contract's trend and Supertrend value (`last_live_bar` in its state); at start, once the ledger, pending requests, roll and missed flip are settled, the seeded series is compared with that mark at the SAME bar, and a different trend or a value more than `seed_st_tolerance_pct` (0.10%, `engine_configs.py`) away raises `SEED DISAGREES with the live chain` (flat or in a trade, and on any restart; skipped for a different contract after a roll or when a flip is pending); (2) `POSITION AGAINST THE TREND`: a position held in the opposite direction to the current Supertrend trend while no flip, request or missed flip is pending, checked at start and after every bar (that includes a flip the engine did not act on), repeated hourly while it stands.

**Supertrend formula (`hestia_core/indicators.py`, changed 2026-10-28 to the standard Zerodha / TradingView one).** ATR is Wilder's (`ewm(alpha=1/period, adjust=False)` of the true range), the raw bands are `hl2 ± multiplier × ATR`, and each FINAL band keeps its previous value until the PREVIOUS close breaks through it (`final_upper[i] = raw_upper[i]` if it is below `final_upper[i-1]` or `close[i-1] > final_upper[i-1]`, else `final_upper[i-1]`; the lower band mirrors this); the line sits on the final upper band until a close above it, then on the final lower band until a close below it. Until 2026-10-28 the engines used a different ratchet that reset the band to its raw value on every bar of the opposite phase. On 28 Oct 2026 that left Hestia's Prometheus band at 9753.38 where Zerodha's stood at 9735.20 after the 15:15 bearish flip, so the 19:45 bar (close 9748) flipped Zerodha bullish and not Hestia, which entered 45 minutes later (20:45, after the 20:30 close of 9763). The new formula reproduces Zerodha's 15-minute Supertrend(10, 2.5) column on 250 CRUDEOILM bars (`tests/test_supertrend_zerodha_fixture.py`, fixture `tests/fixtures/zerodha_crudeoilm_15m_st_10_2.5.csv`); the old formula differed on 39 of 337 bars in that export. The same loop is in `prometheus_backtest/data_loader.py` and `prometheus_production/prometheus_functions.py` (rollback copy), pinned together by `tests/test_supertrend_production_backtest_parity.py`. Every backtest figure produced before 2026-10-28 (the integrated backtest, the compounding simulation, the engine summaries) was computed with the previous formula; over the 2021-2026 history the two disagree on 0.04% to 0.17% of 15-minute bars per instrument and the combined four-engine result moved by about -1.2% (standard formula, to 23 Oct 2026). On the first restart after the change the stored `last_live_bar` marks were computed with the old formula, so a one-time `SEED DISAGREES` or `POSITION AGAINST THE TREND` alert is possible where a band moved by more than `seed_st_tolerance_pct`.

After a restart the persisted ledger is checked against the broker's position book, and the broker wins for live engines. A request that was in flight when the previous process died is **in doubt**: never re-sent, reported `UNCONFIRMED`, and a critical alert asks for the broker to be checked.

## Which machine may trade

Nothing is enabled in the committed `hestia_config.py`. The machine allowed to trade (Delos) has a gitignored `hestia_local.py` naming the engines to enable and their fields; anywhere else `python hestia.py` exits before it logs in, because the session lock and pid checks are per machine and cannot see another machine's process. `python hestia.py --check` prints the no-login start report.

## Roll-eve logic (all four engines, one rule)

The same code serves Prometheus, Selene, Helios and Typhon: `hestia_core/roll_policy.py` (pure rules) and, in each engine's `engine.py`, `_arm_roll`, `_check_roll_timing`, `_execute_roll` and `_coincident_flip_transition`. Read those, not memory, if in doubt. The terms below are used the same way everywhere (docs, Slack, QC).

- **Roll window.** The front contract is rolled out once it has 5 trading days left or fewer, counting the expiry day and counting today (`roll_window_days = 5`, holiday-aware). From the first session on which the front is inside that window, the engine trades the next contract. Hestia refuses any entry on a contract inside the window.
- **Roll eve.** The last session on the old contract: the session after which the next trading day's effective contract is the new one. It is armed when the engine starts that session (log and Slack: "rolling to X tonight at HH:MM; tracking it all day"). All day the engine trades the OLD contract and also tracks the new contract's Supertrend (ST), logging no boundary lines for it. The **rollover time** is the session close minus the engine's `rollover_buffer_min` (14 for Selene, Helios and Typhon, 15 for Prometheus): 23:16 or 23:41 for the three, 23:15 or 23:40 for Prometheus.
- **What happens, case by case on a roll eve:**
  1. **Flat** (at arming or later): the engine switches to the new contract at once. Nothing to protect.
  2. **In a position and the old contract does NOT flip before the rollover time:** at the rollover time the old position is closed unconditionally. It is reopened on the new contract, same direction, only if the new contract's own ST direction at that moment equals the position's direction (the veto) and a basis price exists; the stop and target are recalibrated from the basis (the new contract's price at the time of the old entry). If the new contract's ST disagrees, the engine ends the session flat on the new contract. From the rollover time to the close no fresh entries are made.
  3. **In a position and the old contract FLIPS before the rollover time:** the engine EXITS the old position on `trend_flip` and never reverses on the old contract. If the new contract ALSO flipped to the same direction on the same 15-minute bar (a full window of data), it enters fresh on the new contract in that direction (a new trade, not a carried position). Otherwise it is exit-only: it switches to the new contract flat, and waits for the new contract's own flip, which then is a normal entry (normal guards). The 23:16 roll does not run after this, because the switch has already cleared the roll.
- **Restart cases:** a position on a later contract than today's effective one means an early switch already happened (catch up); a position on an earlier contract means a missed roll (roll now); if the lookup fails the engine refuses to roll backwards and freezes.
- **Never true (common misreadings):** "an old-contract flip on a roll eve reverses into the opposite position on the old contract" (it exits); "a flip on the old contract carries a position to the new contract" (it exits, and re-enters only on a coincident flip); "the 23:16 roll keeps the direction whatever the new contract says" (the veto decides).

## Adding an engine

**Slack wording.** Engine names are capitalised wherever a person reads them (`*Hestia [Selene]*`, the startup line, the session report) through `display.display_name`; logs, file names and the registry keep the lower-case name so greps and paths do not change. The end-of-session report (`reporting.build_session_report`) uses the standalone Prometheus report's layout: a section per engine (instrument, Live or Paper), a block per trade closed this session (entry and exit time and price, reason, points and Rs per unit; an entry from an earlier day carries its date), an Open Position block with unrealised P&L, and a Realized / Unrealized total in Rs per unit; then (added 2026-10-16) a day total in rupees at the units actually traded, Realized / Unrealized / Combined, for the live engines on one line and for any paper engine with activity on a line of its own (never added together; Unrealized reads n/a if an open position had no price); then free cash and, only when present, unconfirmed requests, ledger mismatches and warning-or-worse alert counts. A part-booked position shows only its open lots until the trade closes.

**Fyers candle shadow (Phase 1 of `plans/hestia-fyers-candle-source.md`, built 2026-10-03, off by default).** `hestia_config.CANDLE_SOURCE['mode']` is `'angel'` (nothing changes, no Fyers code runs) or `'shadow'`. In shadow mode Angel One stays the only source any engine sees; `fyers_shadow.ShadowRecorder` asks Fyers for the same one-minute window at every minute tick and records, under `hestia_data/shadow/`, a `polls_<date>.csv` (per poll and side: attempts, whether the just-closed minute was present, how many seconds after the tick, Angel One exhaustion, boundary minute or not) and the closed minutes each source returned with the time each was first seen. It is isolated by construction: its own daemon-thread pool (never joined at exit, never the host's four IO workers), every entry point catches everything, it receives copies of the Angel One frames, it never posts to the kernel or alerts, and a per-token in-flight guard skips a slow Fyers's next minute instead of queueing. `TokenGate` reads `hestia_data/fyers_token.json` (written daily at 06:35 IST by the laptop job) under the same rule as `data_pipeline/fyers_token_refresh.check_token_file` (mode 600, file mtime and `issued_at` both today in IST, before `expires_at`; a test pins the two together), honours the kill-switch flag `hestia_data/flags/fyers_off.flag`, and trips a breaker on an authentication refusal until the token file is replaced. `hestia.py --check` prints the mode and the token state. `research/fyers_mcx_validation/phase1_shadow_report.py --date YYYY-MM-DD` turns a session's files into availability and head-to-head figures and compares Fyers-built Supertrend flips against the boundary lines the engines actually acted on. Enable per host with a `CANDLE_SOURCE` entry in `TRADING_HOSTS` (or `hestia_local.py`); rescue and smart modes are Phases 2 and 3, below.

**Fyers candle rescue (Phase 2 of `plans/hestia-fyers-candle-source.md`, built 2026-10-05, off unless `CANDLE_SOURCE['mode']='rescue'`).** Everything the shadow records, plus one addition: `candle_fetch.fetch_one_minute_window` takes an optional `fallback`, called once after `rescue_after_attempts` failed Angel One attempts (default 5, i.e. only once the whole burst has failed); `FyersRescue.fetch_window` is that fallback. It asks Fyers for the same window and returns ONLY the closed minutes the engine does not already hold (never overwriting an Angel One minute, zero-volume placeholders dropped), and only when Fyers's answer contains the just-closed minute and that minute has settled for `settle_s` seconds (default 0: by the time the Angel One burst has failed the minute has settled). Fyers's first answer for a minute, about 0.07 s after it closes, is provisional: on 2026-10-05 22% to 82% of first-seen minutes differed from the finalized ones, while finalized Fyers differs from Angel One in only 11% to 22% of minutes; a probe (`research/fyers_mcx_validation/settle_probe.py`, 40 samples per offset) found 60% of snapshots final at +0.1 s, 90% at +0.3 s, 95% at +0.4 s and 100% from +0.8 s; before +0.4 s the wrong values are almost all closes off by a few ticks (worst 0.11%). A frame it returns ends the burst; None, an exception, a closed token gate or a refusal leaves the burst exactly as it was. A rescued window is invisible to the engines (same bar, same Supertrend as a failure-free run: a test pins that), logged (`fyers rescue: ... filled N minute(s) from Fyers after Angel One failed`), recorded in `hestia_data/shadow/rescues_<date>.csv`, counted in the end-of-session report, and shown to the shadow's Angel One record as `rescued`, never as an Angel One frame. The shadow's minute files now keep every version of a minute (a minute is written again when a later poll shows different values), so first-seen and settled values can both be compared.

**Fyers candle smart mode, Fyers first (Phase 3 of `plans/hestia-fyers-candle-source.md`, built 2026-10-09, off unless `CANDLE_SOURCE['mode']='smart'`).** For the instruments in `CANDLE_SOURCE['smart_instruments']` (the pilot is `('CRUDEOILM',)`, Prometheus) each minute's poll window is asked of Fyers BEFORE Angel One: `LiveData._cycle` calls `FyersSmart.fetch_window` first and runs the unchanged `fetch_one_minute_window` burst only when it returns None. Three layers sit behind a miss: the Angel One burst (5 attempts), then the Phase 2 rescue (Fyers asked once more after the whole burst failed, in smart mode as in rescue mode), then the recovery queue. `FyersSmart` waits until the just-closed minute is `smart_settle_s` seconds old (default 0.5, the owner's call: the 2026-10-05 fine settle probe found 54% of snapshots final at +0.1 s, 95% at +0.4 s, 97.5% at +0.5 s and all from +0.8 s, the rest being provisional closes off by a few ticks; raise it toward 0.8 in config if suspect closes ever show; one later single pull gives the same value a second pull would, so there is no two-pull confirmation), then pulls; it trusts the answer only if it contains the just-closed minute (a lagging Fyers is retried every `smart_retry_s` up to `smart_max_wait_s` after the minute closed, default 3.0, then handed to Angel One), returns only minutes the engine lacks, never the forming minute, and drops zero-volume placeholder minutes from the frame it returns so the series keeps Angel One's meaning of "an untraded minute is absent", with one exception added 2026-10-14: if the JUST-CLOSED minute itself is a zero-volume row, Fyers is not trusted and the window goes to the Angel One burst at once (no retry, recorded as kind `placeholder`, `served=0`), because Fyers also lists minutes whose trade it had not caught up with (13 Oct 14:36 CRUDEOILM: Fyers answered with the minute empty, Angel One's file has a 3-lot print at 8,734, and the 14:30 bar closed 14/15). An untraded minute therefore costs one Angel One burst, about 1% of CRUDEOILM windows (14 such minutes in the 2 full sessions of 12 and 13 Oct), and still ends absent from the series if Angel One agrees; `CANDLE_SOURCE['smart_confirm_zero_volume']=False` restores the old trust. A placeholder earlier in the window is still just dropped. A rate limit is never retried, an authentication refusal trips the shared breaker, a timeout or error hands over at once, and it never raises. Every Fyers-first window is recorded in `hestia_data/shadow/smart_<date>.csv` (kind, served or not, attempts, seconds after the minute closed, latency, minutes used); a token that is not Fyers-first (other instruments) is still measured by the parallel shadow, a Fyers-first token is not (the shadow would only duplicate the Fyers calls). The host announces `Fyers candle SMART ON for ...`, `--check` describes the mode and the token state, and the end-of-session report counts windows served by Fyers first and windows that fell back. Rollback is the same at every phase: `touch hestia_data/flags/fyers_off.flag` (Angel One only, next poll, no restart) or set the mode back to `'rescue'` and restart.

**Incomplete 15-minute bars: two Slack warnings (reworded 2026-10-14).** When a bar's window is short at the boundary (after the Angel One retries and the Fyers rescue) and a provisional bar could be built from ticks, `LiveData` sends the first warning at the boundary (13:15, 15:00): `<symbol>: 15m bar HH:MM-HH:MM has n/15 minutes at the boundary; provisional bar built from ticks and sent to the engines, the real bar is awaited until HH:MM`. If the window completes before the `deferred_bar_cutoff_min` deadline (1 minute) the bar is delivered as RECOVERED, the engines reconcile the provisional against it and nothing more is sent. If it is still short at the deadline (13:16, 15:01) the second warning follows: `... still n/15 minutes after the 1 min cutoff; the provisional bar was NOT reconciled against a complete real bar, the real bar was built from the minutes on hand` (or `no provisional bar had been built` when there was no tick data or no engine had provisional trading on). The engines still compare their provisional verdict with that partial real bar and log CONFIRMED or DISAGREES. A minute that nobody traded also ends in the second warning, since the count cannot tell untraded from missing.

An `EngineEntry` in `hestia_config.ENGINES` (instrument, `package.module:callable` factory, paper or live, lots per unit, sizing, unit cap) plus the engine package implementing `interface.Engine` against `EngineContext`. No host, flag or report code changes. A new engine is tested against the fake Hestia first, then replayed against recorded days.

## Two engines on one instrument (2026-10-29, for Oleus beside Prometheus on CRUDEOILM)

The data side already allowed it: streams are keyed by token and kept when an engine stops tracking, the poll set is the union over the engines still running, and every bar goes to each engine tracking the token with its own Supertrend settings, so disabling or killing either engine leaves the other with its prices and bars (pinned in `tests/test_hestia_shared_instrument.py` for engines missing from the start, KILLed mid-session and crashed). The broker side is the constraint: Angel One keeps one position row per token AND product type. `register()` therefore accepts a second engine on an instrument if it is paper (it has a book of its own) or if it is live under a different product than the live engine already there (`EngineEntry.product`, CARRYFORWARD by default, INTRADAY for MIS); two live engines on one instrument and one product are still refused. The position book the ledger is reconciled with is keyed by `ports.book_key(token, product)`, which is the bare token for CARRYFORWARD, so everything written before products existed is unchanged; every order carries its engine's product, ghost-order recovery only claims an order of the same product, the start-up bootstrap gives each broker row to the engine that owns its (instrument, product), and a restart corrects each engine against its own row only. An engine may declare `trade_extra_columns`; they are written after the shared 26 columns in its own `<engine>_trades.csv`, so name-based readers of the shared format are unaffected.

## Tests

`python -m pytest tests/` (the Hestia tests are `tests/test_hestia_*.py`; the whole-host tests run a full session in seconds on a simulated clock). Nothing in them can reach a broker; a test asserts that `generateSession` appears in exactly one place (`real_login` in `hestia.py`) and never on import.

**Dynamic sizing: a share of the account's total margin (built 2026-10-17, off unless an engine's `dynamic` is on; `plans/hestia-dynamic-sizing.md`).** Static sizing is unchanged (`static_units`, the unit cap, the live-read override file). With `dynamic` on, whether from config or from the Slack panel's toggle (which writes the override file, read fresh, so it takes effect at the next entry with no restart), each engine sizes on every new entry as `floor((total margin / N) / its own margin_per_unit)`, limited by the unit cap, where total margin is `availablecash + availableintradaypayin + utiliseddebits` from the same `rmsLimit()` answer that feeds `free_cash` (`AngelBrokerPort.total_margin`, same 120 s freshness rule, so a stale or missing reading is 0 and fails closed; the cash value is stored first and a problem computing the total never costs it; the three fields and the total are logged at INFO when the total changes) and N is the number of live engines sharing the account (`HestiaCore.sharing_engines`: registered, on the live pool, not killed; a KILL, a startup DISABLE or KILL gate or a host kill takes an engine out at once, a failed engine still counts, a paper engine sizes against its own paper pool with N = 1, and N is at least 1). The rule is `hestia_core.sizing.dynamic_units`, called by all four engines' `_current_units`. A share below one whole unit is 0, not a forced minimum: the engine warns (`dynamic sizing: share Rs ... is below one unit ...; entry skipped`) and sends no entry, and a flip closes the old position without opening a new one; `_margin_sufficient` refuses 0 units. `allocation_rs`, when set in the override file, is an extra limit on the share. An unexpected exception falls back to the static units with a warning, as before. Each engine's `margin_per_unit` is its own formula; Prometheus and Selene carry a x4 factor (`/3 x4`, `/8 x4`) and Helios and Typhon have had it inside `margin_sizing_multiplier` since 2026-10-17. Check the broker's total against the owner's figure on an ordinary weekday before switching dynamic on.

**When the account's margin is read (2026-10-19).** `rmsLimit()` is no longer polled every 30 seconds. `AngelBrokerPort.start_cash_refresh` reads it once at start and then once `cash_lead_s` (30 s) before every 15-minute boundary of the wall clock (:14:30, :29:30, :44:30, :59:30), on the executor, because every entry and roll happens on a boundary; a failed read is tried once more `cash_stale_refresh_min_s` (10 s) later. The reading is then about 30 s old when an entry is sized, inside `cash_max_age_s` (120 s). A stale or missing reading met by `free_cash` or `total_margin` still answers 0 (the entry is refused) and also kicks one background refresh, at most once per `cash_stale_refresh_min_s`, so the next attempt finds a fresh one. The session report refreshes once before it is built, since the last scheduled read is up to 15 minutes old at the close. Every read logs a `margin read (<why>)` line first (startup, scheduled before the next boundary, retry after a failed read, stale reading met at an entry, before the session report), so the read timing is visible even while the total is constant. The `margin:` log line now compares totals rounded to the paisa, so it is written only when the total changes, not whenever cash and margin used trade places.

**Slack control panel (2026-10-05).** The listener (`slack_listener.py`, a separate service, restart it after a code change and repost the panel) shows one section per engine and one for Hestia, built from `hestia_config.ENGINES`; the logic lives in `slack_bridge.py` so it is tested without Slack (`tests/test_hestia_slack_panel.py`). Every button acts on its OWN flag file only. Per engine: **Exit** writes `EXIT` (refused when Hestia is not running, because the flag would fire unattended at the next start, and when the engine's flag is `KILL`, which a running Hestia would ignore while the EXIT silently replaced the gate), **Kill/Disable** writes `KILL` (it stops a running engine with its position left open, and either way keeps it out at the next start, because the host gates both words), **Clear** removes only that engine's command flag. A killed engine does NOT come back when its flag is cleared: it comes back at the next Hestia start. Hestia: **Start** launches `hestia.py` (refused if the gate is set or it is already running), **Stop/Disable** sets `hestia_disabled.flag` first and then removes `hestia_active.flag` (graceful shutdown, positions left open and unmanaged), **Clear** removes only `hestia_disabled.flag`. The sizing buttons list all four engines and write `<engine>_sizing.json`. The Prometheus-only "Switch Instrument" button was removed. To bring everything back live: Clear the Hestia flag, Clear every engine flag, Start Hestia.

**Session report contents (fixed 2026-10-05).** The report sent at teardown lists every trade whose last exit happened that day, read from each engine's `hestia_data/trades/<engine>_trades.csv` and merged with the trades this process closed (one entry per engine and trade id, the live record winning). Before, it used only trades closed since the process started, so after a mid-session restart earlier trades vanished from it (the 2026-10-05 report said "No trade today" for Prometheus after four closed trades). A trade added to the file by hand is included. An unreadable file contributes nothing and never blocks the report. Tests: `tests/test_hestia_session_report_day.py`.
