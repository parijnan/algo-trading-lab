# Hestia on family members' accounts: plan (second version)

Status: plan only. First version written 2026-10-24; revised the same day on the owner's instructions: the accounts are family, the arrangement is not offered as an algo-provider service, each account trades in isolation on its own signals, and the static IP question is to be planned for in both ways, a shared IP (everything on Delos) and a separate VPS for each account. The owner's own key is registered to the Delos IP address, and the owner is writing to Angel One about sharing it; this version therefore plans both topologies as first-class paths with the work that is common to both done first, and the choice made when the answer arrives (section 3.3). Nothing is built and no code has been changed; every code change below needs the owner's go-ahead before it starts (standing instruction). Companion documents: `plans/hestia-dynamic-sizing.md` (the capital rule), `plans/hestia-p6-cutover.md`, `hestia_core/README.md`. Written as markdown single lines, no hard wrap.

## Background for a reader who does not know this project

This section exists so the rest of the plan can be read cold. Everything here describes the system as of 24 October 2026.

### What exists today

- **The owner** is the person who runs the strategies with their own money and decides everything; the code is written and checked with an AI coding assistant (Claude Code) under the owner's direction. The owner is a retail trader in India, not a firm. The repository is `algo-trading-lab` (on GitHub); this plan is `plans/hestia-multi-tenant.md` in it.
- **Hestia** is the live trading program (`hestia.py` and the `hestia_core/` package). It starts every weekday at 08:55 IST, logs in to one Angel One brokerage account, watches four commodity futures contracts for the MCX exchange all day (the session runs 09:00 to 23:30 or 23:55 depending on the season), decides and places orders, and stops at the close. It holds no strategy of its own: it hosts **engines**.
- **The four engines** each trade one MCX instrument with a Supertrend trend-following rule on 15-minute bars: **Prometheus** (CRUDEOILM, mini crude oil), **Selene** (SILVERMIC, silver micro), **Helios** (GOLDPETAL, gold petal) and **Typhon** (NATGASMINI, mini natural gas). Supertrend is a standard trend indicator that flips between "up" and "down" when price closes through a trailing band; each engine enters when the trend flips, exits on the opposite flip or on a stop (and, for Prometheus and Typhon, on profit targets), can hold positions overnight and across days, and rolls onto the next monthly contract before expiry. Parameters differ by engine (Supertrend multiplier 2.5, 2.5, 3.5 and 3.0; stops of 1.0%, 3%, 1.6% and 0.8% of the entry price). Each engine holds at most one position at a time.
- **A unit** is the engine's sizing step: Prometheus 2 lots, Selene 1 lot, Helios 20 lots, Typhon 2 lots (a lot is the exchange's contract size). The owner's own account runs 5 units of every engine from Monday 26 October 2026 (Prometheus 10 lots, Selene 5, Helios 100, Typhon 10), up from 2 units the week before. Units are set by hand in `hestia_config.py`; a dynamic rule (units from a quarter of the account value over each engine's margin per unit, rounded down) is built but switched off.
- **Where it runs.** **Delos** is the owner's production server: a Linode VPS (Ubuntu 24.04) with a static IP, where Hestia runs under cron, where a 23:56 cron job downloads the day's candle data and runs `git pull`, and where all runtime state lives (`hestia_data/`, `logs/`). The owner develops and backtests on a laptop and reaches Delos over SSH (every command that touches Delos needs the owner's explicit approval, by standing rule). Code goes laptop to GitHub to Delos. The laptop also refreshes a Fyers market-data token every morning at 06:35 and pushes it to Delos.
- **The broker and the data.** Orders go through **Angel One's SmartAPI** (a REST API plus WebSockets) on the owner's own account; the login needs an API key, the client code, a PIN and a TOTP code (a 30-second code generated from a stored secret, the same thing an authenticator app does). **Angel One allows one active API session per account**: a second login anywhere cancels the first session's ability to place orders (error AB1007). The same account's candle requests sometimes hit a rate-limit warning (AB1021) that Hestia retries; it is known and tolerated. A second data source, **Fyers**, is polled first for each minute's candles, for crude oil since 12 October and for all four instruments from Monday 26 October (Angel One is the fallback).
- **Slack** carries the notifications: session lifecycle, entries and exits, closed trades, periodic in-trade profit updates, and errors, into four channels; a small separate program (`slack_listener.py`) also handles buttons in Slack that stop or start Hestia and change sizing.
- **Tools around it** (all in the repo): backtests of each engine and a combined backtest, the Hestia Dashboard (a web page of live results), a compounding simulation with real charges and slippage, and QC checks of every session. These are mentioned in the plan only where they must become account-aware.
- **Paper and live.** Hestia can run an engine in paper mode (decisions and a fake ledger, no orders). Live orders started on 1 October 2026 (Selene) and 2 October (Helios, Typhon); Prometheus has traded live since September.

### What the results look like, so the commitment is clear

- The strategies are backtested on three to five years of real contract data, one real contract at a time. For one unit of each engine, the combined backtest from April 2021 to October 2026 is about Rs 16.4 lakh gross with a worst closed-trade drawdown of about Rs 58,600, and long losing runs occur (19 or more trades in a row in the simulated books). Only about 80 trades have been live so far (a few weeks); they match their backtest twins closely in the entries and exits and differ by a small average slippage.
- After brokerage, taxes and slippage, and at small capital, the result is much lower: simulated on Rs 4 lakh from April 2023 the account ends at about 3.1 times in 3.5 years, with a deepest closed-trade drop of about 18%, and most of the profit arriving in 2026. Roughly 90% of the profit comes in the last year. The family accounts would be exposed to the same drawdowns, scaled to their own capital, and to the same trades at the same time as the owner.

### Terms used in the plan

- **Account, tenant, member.** An *account* is one family member's Angel One trading account. A *tenant* (used for Option S) is the software's own name for one account's setup on a shared machine: its own credentials, state, logs and settings. A *member* is the family member who owns the account.
- **Option S, Option V, Option M, hybrid.** S: all family accounts run as separate processes on the one shared server (Delos), sharing its IP address. V: each account has its own small rented server (a VPS) with its own IP address. M: one server with several IP addresses. Hybrid: some of each. Section 3 explains them.
- **Static IP.** SEBI's retail algo rules, as brokers apply them, require that API orders come from an IP address registered with the broker for that API key, and the address must stay fixed. Angel One's version is reported to be IPv4 only and, per community posts, one IP per app; this is the question put to Angel One in Appendix A.
- **API app, API key.** A member creates an "app" in Angel One's SmartAPI portal for their own account, which gives an API key; the key plus the member's client code, PIN and TOTP secret is what lets software trade the account.
- **Session lock, ledger, flags.** Hestia's own bookkeeping: a lock file that stops two of its own processes logging in to the same account; a ledger of the positions it believes it holds (checked against the broker's book); and small flag files that stop or disable the whole host or one engine.
- **Heartbeat.** A short status message each machine would send twice a day.
- **Canary.** The owner's own account, which receives every code change first, before any family account.
- **Gate, outcome A to E.** The decision table in section 3.3: the answer from Angel One selects the topology.
- **QC.** A read-only check of a trading session against the code, configuration, state files and Slack, done each day by the assistant.
- **Parity report.** A daily comparison of each account's entries and exits with the owner's, to show that independent copies stay close to each other.

### What this plan is and is not

It is a design and sequencing plan for letting a few family members run the same four engines on their own broker accounts, hosted by the owner. It is not a product plan for outside clients (section 0.2 lists what would change that), it contains no code, and it records the open questions that need answers from the broker before anything is built. The owner has asked for both a shared-IP route and a separate-VPS route to be planned in full.

## 0. Scope, assumptions and the few things still to confirm

Assumptions given by the owner: every account belongs to family; Hestia sits on top of the family member's own broker account and helps them trade, it is not sold as an algo-provider service; each account executes on the signals its own process computes, in isolation, so there is no ordering between accounts and nothing to front-run; the family member owns the account, the capital and the risk, and the owner runs the software. This plan takes that as the frame. What remains to confirm is short and mostly about the broker, not about the strategy. Nothing here is legal advice; the points come from broker FAQs and forum threads (listed at the end) and not from the SEBI or NSE circulars themselves, so each needs one written confirmation.

- **0.1 Who counts as family.** The retail algo summaries describe the family allowance as self, spouse, dependent children and dependent parents. Brokers such as Fyers apply the same list when they allow a shared static IP. Before an account is added, check that its holder falls in that list as the broker applies it; a sibling, an adult independent child, in-laws or cousins may not.
- **0.2 What would bring the larger questions back.** A fee or a share of profit, an account outside the family list, or an arrangement in which the owner takes discretionary trades for someone who is not following along. If any of these appears, the questions from the first version (algo-provider registration and empanelment, portfolio-management or advisory status, the broker's terms for third parties) return and the plan stops until they are answered. The plan assumes none of them.
- **0.3 Registration of the algo.** The summaries say self-developed algos need registration only above an order-per-second threshold, and Angel One's SmartAPI notice caps order requests at 9 a second. Hestia places a handful of orders a day per account, far below that. Confirm with Angel One that a self-developed algo used by the account holder's family needs nothing further, and that "used by the family member's account, run for them by the owner" is the same thing in their eyes.
- **0.4 Credentials.** The login needs the member's API key, client code, PIN and TOTP seed (`data/user_credentials.csv`: `api_key, user_name, password, qr_code, slack_token`, read by `hestia.py` `real_login`). Confirm with Angel One that an unattended login with a stored PIN and TOTP seed on the owner's server is acceptable for a family member's account, or whether the framework's OAuth-style login applies to API keys now. If a consent-style login is required, the 08:55 unattended start needs redesign; this decides the credential design (D5).
- **0.5 Written authority and disclosure.** A short signed note from each family member: they authorise the owner to run Hestia on their account, they have seen the real figures (the drawdown, the worst trade, the cost of charges and slippage), they keep control (they can stop it, withdraw funds, revoke the API key at any time) and they accept the risk. This protects the relationship as much as anything regulatory.
- **0.6 The owner's own key.** Settled by the owner: the key is registered to the Delos IP address. Angel One's announcement, as reported on its SmartAPI forum, says both key types keep working for now and users are expected to migrate to static-IP keys, so the owner's key is already on the right side of that. Two checks remain, both cheap: that Delos's outbound orders really leave from the registered address (Delos has IPv6 and IPv4, only IPv4 is reported as supported; log the public IPv4 an outbound request shows), and what the second (secondary) IP field on the app is for (it could hold a failover address). One new point for the Angel One letter: whether registering the Delos IP on other accounts' apps changes anything for the owner's own registration (3.1 and Appendix A).

## 1. What is being asked

Family members run the same four engines (Prometheus, Selene, Helios, Typhon on the four MCX instruments) on their own Angel One accounts with their own capital, hosted by the owner, in parallel with the owner's own account (5 units each from Monday 26 October 2026). Slack stays manageable: the periodic in-trade updates are skipped for the family accounts, everything else is replicated. Questions: how to handle the static IP, whether to use one host or a VPS per account, and how git pushes and pulls work across instances.

Assumed scale: up to 3 family accounts for the pilot, designed to about 6. Per account: the four engines, static units set by the owner with the member's agreement, no dynamic sizing at first.

## 2. How the system is built today (what matters here)

- **One account, one process, one data directory.** Every path is a constant relative to `REPO_ROOT` in `hestia_config.py`: `hestia_data/` (state, ledger, flags, cache, trades, running rows, the Fyers token, shadow records, `angel_session.lock`), `logs/hestia_<date>.log`, `data/user_credentials.csv` (one login row). Nothing takes the account as a parameter.
- **Config is keyed by hostname.** `TRADING_HOSTS` (in git) and the optional gitignored `hestia_local.py` resolve engines, units, the unit cap and the candle source. The local file overrides only `ENGINES`, `SLACK_PROMETHEUS_VIA_HESTIA` and `CANDLE_SOURCE`; the Slack channel names are plain constants.
- **The session lock is per data directory.** A second `generateSession` on the same account from anywhere evicts the first session's order capability (AB1007). Two tenants in different directories would not know they share an account.
- **Slack:** fixed channel names (`#tradebot-updates`, `#trade-alerts`, `#trade-updates`, `#error-alerts`), one bot token in the credentials row, and `slack_listener.py` (a separate daemon) handling the buttons for one set of flag files. A channel set to empty is simply not posted to (`slack_queue.send` returns when the channel is empty).
- **Deployment is a nightly pull.** `data_pipeline/run_mcx_downloader.sh` (cron 23:56 on Delos) does `git pull` and logs in to the owner's Angel One account to download candles, so every push to `main` is live at the next 08:55.
- **Market data:** each process fetches its own candles from Angel One and, in smart mode (all four instruments from Monday), from Fyers first, using one token file the laptop job writes at 06:35 and pushes to Delos. Two WebSockets per process.
- **Margin per unit** (x4 buffer included): Prometheus about Rs 1.25 lakh, Selene 1.07, Helios 1.09, Typhon 1.12, so one unit of all four is about Rs 4.5 lakh and the capital rule needs about Rs 5 lakh to take one unit of each; the owner's 5 units need about Rs 22.6 lakh.

## 3. The static IP, and where each account runs

### 3.1 What is reported about the rule (community-reported, undated, to be confirmed with Angel One)

- A static IP is needed for order placement and GTT only; other API calls do not need it. Orders must leave from the whitelisted address. Both key types work for now; migration to static-IP keys is expected.
- IPv4 only is supported for now, IPv6 promised. Delos has both; the registered address must be an IPv4 that the orders really leave from.
- A primary and a secondary IP field exist; the secondary's use is not explained anywhere found.
- Registering the same IP for a second account returned "Primary Static IP is already associated with another app", and one user wrote that the same IP could not be reused even for verified family accounts. Fyers, by contrast, has an explicit facility for a common static IP for family members (spouse, dependent parents and children, subject to KYC), and Zerodha users report a "linked to another account" error when adding a family member's IP separately. So the practice differs by broker and may differ by Angel One's implementation.
- Order requests are capped at 9 a second and all sessions are logged out at midnight.

The decisive question for the owner to put to Angel One in writing: **can one static IPv4 be registered on the API apps of several verified family members' accounts, and if so by what procedure?** If yes, one host is enough. If no, each account needs its own IPv4.

### 3.2 Hosting options

- **Option S, one shared host (Delos), one process per account.** All family processes run on Delos, sharing its IPv4. Needs a yes to the question above. Cheapest to run and to update (one machine, one checkout, one set of tools). Needs the multi-tenant code in section 5 so processes do not share paths, credentials or locks, and a fail-closed rule so a missing tenant name can never fall back to the owner's account. One machine is also one point of failure and one point of compromise for every account's credentials.
- **Option V, a separate small VPS per account.** Each family account gets its own VPS with its own static IPv4, registered on that account's API app only. Each VPS is a single-account copy of today's setup: its own `data/user_credentials.csv`, its own `hestia_data/`, a `hestia_local.py` for its units and engines, its own cron line. **No tenant selector or path refactor is needed**, because every machine is already a one-account machine, and an isolated credential store, lock file, log, flag set and failure domain come for free. A compromise of one VPS exposes one account. The static IP story is the cleanest possible (one IP, one account, the VPS can even be billed to the account holder). The costs are operational: N machines to provision, update, watch and pay for (a small Ubuntu 24.04 VPS is a few hundred to a thousand rupees a month each; measure Delos's real memory and CPU for one Hestia process first to pick the size), more per-host approvals under the CLAUDE.md protocol, and the data distribution problem in 3.4.
- **Option M, one host with several IPv4 addresses.** One VPS with an extra public IPv4 per account, each process binding its outgoing connections to its own address. Keeps one machine but needs source-address binding in every Angel One call and in the WebSockets (the SDK uses plain `requests`; this is a patch to the SDK usage and an adapter on every session), a provider that sells extra IPv4s, and per-source routing. More engineering than S or V and fragile. Not recommended unless S is refused and V is too heavy.
- **Hybrid.** Shared Delos for the accounts for which the broker allows the shared IP (for example spouse, dependent parents) and a VPS for any account where it does not. The code needs S's multi-tenant plumbing only if two or more accounts share Delos.

### 3.3 Planning for both: the decision after Angel One answers

Both topologies are planned in full below and in sections 5 to 8, and the work that serves either is done first (5.0). The topology is chosen from the written answer to the question in 3.1:

- **Outcome A, one IP may be registered on every family member's app.** Option S for all family accounts on Delos, with Option V kept as the escape hatch for any account Angel One later refuses. Build the multi-tenant layer (5.2).
- **Outcome B, shared only for some relationships, or per-account approval and KYC steps.** The hybrid: eligible accounts on Delos (Option S), the rest on a VPS each (Option V). Onboarding includes the eligibility check (0.1). Build 5.2 for the accounts on Delos.
- **Outcome C, one IP per app, no sharing.** Option V for every family account, Delos for the owner only. Do not build the multi-tenant layer: it would serve nobody.
- **Outcome D, sharing is allowed but registering Delos's IP on other apps affects the owner's own key** (for example the IP is bound to one app). Treat as C: the owner's key and live trading come first.
- **Outcome E, no clear answer yet.** Pilot on one VPS (Option V): it is isolated by construction, cannot touch the owner's key or session, needs only 5.0 and 5.1, and everything learned on it (provisioning, heartbeat, deploy, QC, the member's experience) carries over to either topology.
- **A VPS is always available as a fallback** for one account under any outcome, so a shared-IP answer never blocks onboarding a member whose relationship or KYC does not fit.

### 3.4 What a VPS per account needs (Option V in detail)

- **Provisioning (once per VPS, written as a checklist or a script, nothing improvised):** Ubuntu 24.04, a non-root user, SSH keys only, firewall closed inbound except SSH, outbound open, `chrony` time sync (TOTP is time-based), the same Python environment as Delos (the conda path used by the cron lines), a read-only deploy key for the repo, logrotate, a cron line for 08:55 with `flock`, the `hestia_local.py`, the credentials file (mode 600), `hestia.py --check` clean, the provider's static IPv4 reserved (rebuilding the VPS changes the address and the broker registration must be redone).
- **Candle files for seeding.** Each process seeds from `data_pipeline/data/mcx/` which the owner's 23:56 downloader fills with the owner's login. Options: (a) the VPS pulls the data directory from Delos each night over a restricted key that can only read that directory (a compromised VPS then exposes only market data, not Delos); (b) the VPS runs its own copy of the downloader with that account's login (more load on that account, a second login risk at 23:56 only when nothing trades); (c) the laptop pushes. Recommendation: (a).
- **The Fyers token.** The owner's token is pushed daily to Delos from the laptop. Pushing it to each VPS means the laptop job learns N targets and the owner's Fyers token lives on each family VPS; check Fyers's terms for that use. Alternatives: each family VPS runs Angel One candles only (the setup until 5 October, with the AB1021 noise Angel One's own capacity produces) or each member has their own Fyers token. Recommendation for the pilot: Angel One candles only on the family VPSs (smart mode off in their `hestia_local.py`), revisit once the pilot is stable.
- **Slack.** Channel names are constants today. Needed change (small, part of the common core 5.0 and 5.3): let `hestia_local.py` set the channel names and a message tag, so a family VPS posts to its own channels and tags every message. `SLACK_TRADE_UPDATES` empty for these machines gives the "no periodic updates" behaviour as asked. The owner's own channels stay as they are.
- **A guard against the wrong credentials on the wrong box.** An `EXPECTED_CLIENT_CODE` in the machine's `hestia_local.py` and a preflight check that the credentials file's client code matches it, and that the VPS's public IPv4 matches an `EXPECTED_PUBLIC_IP`. Small code change (part of 5.0).
- **Updates and git.** Section 7. A tag-pinned checkout, updated by a deploy script run from the laptop over SSH, one host at a time, after the close.
- **Monitoring.** Each VPS posts a heartbeat at 09:05 and 23:45 (process alive, engines up, positions, free margin, errors, last candle time) to its own channel and to the owner's `#family-ops` channel; the owner's morning check is one message per account. `hestia-qc` and `hestia-dashboard` take a host alias (an SSH alias per VPS), each command approved per CLAUDE.md.
- **Backups.** Nothing on a VPS is the only copy of anything important except the account's own trade history; the trade CSVs and state are copied to the owner's laptop weekly over a read-only pull. Credentials are not backed up anywhere except where the member keeps them.

## 4. Decisions (each with a recommendation)

- **D1. Independent copies or leader and followers?** Independent, as the owner says: each account's process computes its own Supertrend from its own candle fetches and trades on its own signals; there is no coordination between accounts. A leader-follower design would couple every account to the owner's process and account for no benefit the family needs. A daily parity report (each account's entries and exits against the owner's: time, side, price, units) is kept as a quality check, not a compliance measure: small differences in fills and in provisional bars between accounts are expected and the report shows when they stop being small.
- **D2. Market data load.** Option V removes the shared load entirely (each VPS has its own Angel One account's limits; Fyers is off for the pilot). Option S multiplies Angel One bursts and Fyers pulls by the number of processes on one machine and one token: measure before adding the third account (are Angel One's limits per account or per IP; what are Fyers's limits per app). If it binds under S, a shared minute-bar feed that every process reads is the remedy.
- **D3. Slack and notifications.** Two layers as in the first version. The owner's ops layer: new channels `#family-ops` (lifecycle, entries, exits, closed trades) and `#family-alerts` (warnings and worse), every message carrying the account tag, plus the heartbeat. The member's layer: their own private channel in the owner's workspace (invited as a guest if they want to see it), or an email summary, with session start and stop, entries, exits, closed trades, errors that concern them and the end-of-day report; `trade-updates` off. The listener's panel selects an account, only the owner's Slack user id may press anything, and a stop-all button sends the stop flag to every host (a per-host command under Option V, one flag per tenant under Option S).
- **D4. Sizing and capital.** Static units per account and a unit cap, set by the owner with the member's agreement and reviewed monthly; the Slack sizing override stays the owner's. The dynamic rule stays off until the owner has run it on his own account. A minimum capital for any account is set from the simulation: the Rs 4 lakh case ends at 3.1 times in 3.5 years with charges and slippage taking 43% of gross profit and entries skipped for months because a quarter of the account is below one unit's margin; task: extend `hestia-simulation` with a start-capital control and run Rs 5, 10, 15 and 25 lakh to set the minimum and the units by capital band (expectation: not below Rs 10 lakh). The member keeps free cash for the worst case, whatever the formulas say.
- **D5. Credentials.** Depends on 0.4. If a stored PIN and TOTP seed are allowed: a file per account outside the repo, mode 600, never in git or logs; under Option V it lives only on that account's VPS, which is the strongest isolation available; under Option S one file per tenant, preferably one Linux user per tenant. The SmartAPI logger leaked credentials once (closed 2026-09-09 by a 13-file suppression): confirm the suppression is active in every entry point on every machine. A dedicated API app per account, revoked and rotated at any exit. State plainly to the member: a stored PIN and seed is control of the account, so whichever machine holds it is the thing to protect (SSH keys only, firewall, updates, no other services).
- **D6. Hosting topology.** Section 3.3: plan both; the owner writes to Angel One; the outcome table decides. Until the answer, only the common core (5.0) is built and a pilot, if the owner wants one earlier, runs on one VPS.
- **D7. Code and release management.** Section 7.

## 5. The code changes this implies (none started; each needs the owner's go-ahead)

### 5.0 The common core (serves both topologies; first to build, once the owner agrees)

- **One account-file schema** read the same way under either topology: account name, expected client code, expected public IPv4, engines on or off and paper or live per engine, static units and unit cap per engine, candle-source mode, notification sinks and levels, the Slack tag, the member's capital for the record, start date. Under Option V it is the machine's gitignored `hestia_local.py` (or a file it loads); under Option S it is one file per tenant. Designing it once means the same tools, checks and statements work either way.
- **Slack channel and tag overrides**, `trade-updates` empty for family accounts (5.3).
- **The expected-identity preflight** (client code from the credentials file against the account file, the public IPv4 an outbound request shows against the registered one), useful on a VPS and just as useful on a shared host where a mistaken credentials file would put one member's orders on another's account.
- **The heartbeat and fleet message.**
- **Release tooling shaped for a list of targets:** the deploy script takes a tag and a list of (host, account) pairs, so it works for one shared host with several tenants, or several VPSs with one account each, or a mix.
- **Account-aware tools:** `hestia-qc`, `hestia-restart`, `hestia-dashboard` take an (SSH host alias, account) pair.
- **A parity report and a monthly statement** built from per-account trade files, whatever the host.

### 5.1 Single-account machines (Option V): what is on top of 5.0

- **Nothing beyond 5.0 is needed in code:** each machine already is a single-account machine, so the channel overrides, the identity preflight and the heartbeat of 5.0 are the whole of it. Default (no local file) behaves exactly as today.
- **Sizing and engine selection** need nothing new: `hestia_local.py` already overrides `ENGINES`, units and the cap per machine, and a machine's file is never in git.
- **A hostname guard:** `TRADING_HOSTS` is in git and keyed by hostname; family hostnames and units must live only in each machine's `hestia_local.py`, never in `TRADING_HOSTS`.

### 5.2 The shared host (Option S): the larger change, built only for outcomes A and B

- **A tenant selector** (`--tenant` or `HESTIA_TENANT`) resolved before any path or login, and the single source of `HESTIA_DIR`, `STATE_DIR`, `FLAG_DIR`, `CACHE_DIR`, `TRADES_DIR`, `LOG_DIR`, `SESSION_LOCK_FILE` and `CREDS_FILE`, which are import-time constants today. Tenant homes outside the repo (`~/tenants/<name>/`); the owner becomes the tenant `owner`, mapped to today's layout so his live data does not move.
- **Fail closed:** on Delos a process with no tenant set refuses to start, so a mistake can never fall through to the owner's credentials, evict his live session (AB1007) and trade at his 5 units. The owner's cron lines set `HESTIA_TENANT=owner`.
- **Preflight:** credentials file mode 600; the client code not already used by another running tenant (a registry of tenant, client code and pid); units within the cap; the margin check at the chosen units against free cash; sinks reachable; the logger suppression active.
- **A task list of every other single-account assumption** (confirm and, where needed, make tenant-aware): `hestia_config.py` (paths, `CREDS_FILE`, `LEGACY_PID_FILES`, `SLACK_PROMETHEUS_VIA_HESTIA`), `hestia_core/preflight.py`, `slack_bridge.py`, `fyers_shadow.py`, `recorded.py`, `session_lock.py`, `slack_listener.py`, `hestia_performance/pull_snapshot.py` and `tracker_config.json`, the Fyers token scripts (`fyers_token_refresh.py`, `fyers_auto_token.py`, `run_fyers_auto_token.sh`: one shared token file, not copied per tenant), the downloader scripts (stay on the owner's login and never read a family file), `prometheus_engine/seed_state.py` and `replay_check.py`, `research/fyers_mcx_validation/*`, the Hestia tests and `tests/hestia_host_helpers.py`, the skills `hestia-qc`, `hestia-restart`, `hestia-dashboard`, `hestia-backtest` (step 4), `hestia-simulation`, `CLAUDE.md` and `hestia_core/README.md`.
- **A lazy-import inventory:** any `import` inside a function in `hestia_core` or the engines can load a file from the checkout after a `git pull` during a session and give a process half old and half new code; list them (it matters for the owner's own checkout, and for Option S's shared checkout).

### 5.3 Under either option: notifications

A small notifier layer in front of `slack_queue.py` and `alert_router.py` carrying the tag and a level per message and a list of sinks per machine or tenant (channel or email), with `trade-updates` excluded for family accounts; the end-of-day report built per account; the fleet message for the owner built from the heartbeats (V) or the state files (S).

### 5.4 Broker-side changes that 0.3 and 0.4 may bring

Order tagging, an OAuth-style login, a per-account API key and IP registration step. Not designable until Angel One answers.

## 6. Operations

- **Process model.** Option V: each VPS has the owner's 08:55 cron line shape (with `flock`), nothing else running. Option S: one cron line per tenant, a minute or two apart before the 09:00 open, a screen session per tenant, the host flag per tenant. Measure how long a login and the seeding take (seeding is where the AB1021 noise clusters) before choosing the gap.
- **Restarts.** Today's restart rule (any time, the recovery path is trusted) holds for the owner. For a family account, prefer after the close and before the next start, unless an emergency; the per-account stop flag stops one account only.
- **Fleet health:** the heartbeat messages (09:05, 23:45), a missing 09:05 heartbeat is an alert on its own; the owner's one-message morning check.
- **Tools:** `hestia-qc`, `hestia-restart` and `hestia-dashboard` take an account (an SSH host alias under Option V, a tenant under Option S); the dashboard's live-start ids per account; the backtest comparison per account; each Delos-or-VPS command approved per CLAUDE.md (the protocol extends to every VPS: host, path and read-or-write stated first).
- **Parity and quality:** the daily parity report (D1), the broker-versus-ledger reconciliation per account (already in Hestia), AB1021 and Fyers-failure counts per account, slippage against the backtest per account. Persistent differences are investigated and explained to the member.
- **Statements.** A monthly statement per member: trades, units, gross result, the broker's own charges from the contract notes, slippage, net, engine on-off history, sizing changes. The member's own Angel One statements remain the source of truth for money.
- **Incident playbook:** AB1007 (the member or another platform logs in to the same API session), TOTP drift (time sync), broker maintenance or session expiry (all sessions are logged out at midnight), a member withdrawing funds so entries are refused for margin, a member asking to stop (flatten, disable, revoke), a machine that will not seed, a bad release (previous tag), the static IP changing (a VPS rebuilt, a provider event: orders fail until the broker registration is updated: put this first in the playbook), and a stop-all.

## 7. Git: how pushes and pulls work with several instances

The risk to manage: today every push to `main` reaches Delos at 23:56 and the next 08:55 start runs it. That is acceptable for the owner's own capital and should not be the rule for a family member's.

- **One repo, no account data in it.** Family names, units, account ids, credentials, state and logs never go into git (public or private repo): under Option V they live in each machine's gitignored `hestia_local.py`, `data/` and `hestia_data/`; under Option S in `~/tenants/`. `TRADING_HOSTS` keeps only the owner's machines.
- **Releases are tags on `main`** (`prod-YYYYMMDD-N`). The owner's own tenant on Delos (the canary) tracks `main` and keeps the nightly pull. Family accounts run a tag. Promotion rule, written down: the commit has run in the owner's tenant for at least 3 full sessions with a clean `hestia-qc`, no unexplained error, the tests pass (`python -m pytest tests/`), and the notes say whether a local-file schema, credentials or a restart is affected.
- **Option V mechanics.** Each VPS has a checkout detached at a tag and never pulls on its own (no downloader cron). A deploy script, run from the laptop, takes a tag and a list of hosts and, host by host, after the close: stops the process by its flag, confirms it is gone, `git fetch --tags` and checks out the tag, runs `hestia.py --check`, starts it, reads the first log lines and posts the result. A rollback is the same command with the previous tag. One host first, then the rest.
- **Option S mechanics.** A second checkout `~/hestia-release` on Delos, detached at the tag, runs every family tenant; the same stop, checkout, check, staggered start after the close; its `data_pipeline/data` is a read-only link to the main checkout's directory so one downloader serves everyone.
- **After-close promotion removes the lazy-import hazard** for family processes: the working tree changes only while no family process runs.
- **Hotfixes:** fix on `main`, test, tag, promote out of hours; an emergency during a session is a stop-that-account action first, then the same path.
- **Config changes need no push.** A change of units, engines or channels is an edit to that machine's local file (or tenant file) and a restart of that machine's process; only code and the owner's own `hestia_config.py` go through git.
- **Local-file compatibility.** A schema change to `hestia_local.py` ships in code that still reads the old one for a release, with a migration note, and a test builds a local file from fixtures so a break fails in CI and not at 08:55.
- **Skills and docs** are repo-local (`.claude/` is gitignored on the laptop): the account-aware skills run on the laptop and reach each machine over SSH with the per-command approval protocol.

## 9. Onboarding and offboarding (draft)

Onboarding: the family list check (0.1); the signed note (0.5); the member's capital and risk appetite recorded; commodity segment enabled and margin available on their account; API app created and, under Option V, the VPS's IPv4 registered on it (or the shared IP under S, if allowed); credentials delivered by an agreed secure route and stored per D5; the local file with paper mode and the agreed unit schedule; `--check` clean including the identity guard; a paper week; the live ladder; the member receives their notification sink and a one-page note on what the algo will and will not do; the first-day QC is shared.

Offboarding: flatten and disable (EXIT then KILL), confirm no open orders or positions, revoke the API key and the IP registration, delete the credentials and the local file, archive the trades and statements, final statement, remove the cron line and the sinks, and (Option V) destroy the VPS or keep it for the next member.

## 10. Risks that stay

- Angel One's actual stance on the static IP for family accounts, on stored credentials and on the owner operating a family member's key (0.3, 0.4, 3.1): it can delay or reshape the service, and it can affect the owner's own account if the broker disagrees.
- Under Option S one host is a single point of failure and compromise for every account; under Option V every machine is its own failure and the cost is operational discipline.
- Correlated outcomes: every account takes the same trades at the same time, so the owner's worst day is each member's worst day scaled to their capital.
- A rebuilt VPS or a provider event changes the IPv4 and stops orders until the registration is updated.
- Capital too small for the rule (the simulation's lesson): after charges and slippage the result at one or two units is far below the backtest.
- Support load: every question from a member is a QC of that account's day.
- The family dimension: losing days happen; the signed note, the disclosure of the real figures and the monthly statement are what keep trust.

## Appendix A. Draft questions for Angel One (in writing)

Context to state: I hold an Angel One account with a SmartAPI app whose static IPv4 is registered; I run my own self-developed trading software on a VPS. I want to run the same software on the accounts of immediate family members who hold their own Angel One accounts, on my server, with each family member's own API app and credentials, and with their consent. There is no fee and no profit share. Questions:

1. May the same static IPv4 address be registered on the SmartAPI apps of several family members' accounts (spouse, dependent children, dependent parents; please state the exact list you accept)? If yes, what is the procedure (forms, KYC, relationship proof, written consent, processing time)? If no, is the rule one static IP per app, and does it apply across accounts of the same family?
2. If the same IP is registered on other family members' apps, does that change anything for the registration on my own app (for example "already associated with another app")?
3. What are the primary and secondary static IP fields for? May the secondary be a different address for failover? Is IPv6 supported yet?
4. For orders the API accepts only the registered IP: do you also check the IP for login and market-data calls? What happens when the registered IP changes (a server rebuilt on a new address): how fast can it be changed, and is there a cool-down?
5. The software logs in unattended at 08:55 with the member's API key, client code, PIN and TOTP seed, and places a small number of orders a day (well under the 9 a second limit). Is a login with a stored PIN and TOTP seed on my server acceptable for a family member's account, or is another login method (consent or OAuth style) required for API apps? If required, from when?
6. Does a self-developed algorithm used on immediate family members' accounts need to be registered with you or the exchange, and if so under what threshold or conditions? Which algorithm identifier tagging do you require on API orders and from when?
7. May I run the software from a server I control, with each member's key, or does each member need to run it from a server in their own name? Is a VPS billed to a family member's name preferable?
8. Is there any restriction on one person managing several family accounts' API sessions from one address (rate limits per IP, abuse detection)?
9. Both key types (with and without a static IP) still work: is there a date after which keys without a static IP stop working?
