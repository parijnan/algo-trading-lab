# Plan: Prometheus Phase 3 — Production Architecture

**Status: DRAFT, first pass (2026-09-01).** Builds on `prometheus_production/` (Phase 2's build — see `plans/prometheus-phase2-production.md`), not a rewrite. Most of the process architecture — contract resolution mechanics, ST seeding, resilient polling, order execution, fill verification, guardian check, circuit breaker, sizing, state persistence pattern, Slack reporting — carries over. What's genuinely new is a single problem Phase 2 never had to solve: **a position can now be open at the moment a contract needs to roll.** Everything below either reuses Phase 2 unchanged, simplifies it (no EOD flatten), or exists specifically to handle that one new problem.

**The 2.0-vs-2.5 multiplier decision is still pending** (`prometheus_backtest/README.md`'s Phase 3 section) — this plan is written to be agnostic to it; whichever wins just fills in `ST_MULTIPLIER`/`SL_PCT`/`TARGET1_PCT`/`TARGET2_FLAT_PCT` in `configs_p3.py`'s production counterpart. Nothing below depends on which candidate is chosen.

**Several sections are marked OPEN — genuine decisions, not filled in yet.** Don't treat this document as ready to build from until those are resolved.

## 0. What reuses unchanged from `prometheus_production/`

- `resolve_effective_contract()` — the tender-margin-early-roll mechanics (`TENDER_ROLL_TRADING_DAYS`, `_count_trading_days_inclusive`) are reused **as the underlying primitive**, just called differently (§4) — no changes to the function itself.
- `seed_st15`, `compute_st`, `backfill_contract_if_needed`, `_tail_read_contract_csv` — ST seeding/computation, including the "no cross-contract stitching" rule (each contract gets its own Supertrend from scratch).

## 1. Resilient order execution — port ghost-order recovery into `place_order` [DECIDED 2026-09-03]

**`place_order` (`prometheus_functions.py:716-739`) is not the same pattern the README's "Resilient Order Execution" section describes for the rest of this repo's live strategies, despite §0 previously implying it was reused unchanged.** Traced this precisely: Prometheus's version was ported from Iris's (`iris_functions.py:563-596`), which is structurally identical — a single `try`/`except Exception` around `placeOrderFullResponse`, returning `None` on any failure. Iris's own code says why it's simpler: *"Iris has no RMS/order-book polling like Artemis/Athena"* (`iris_functions.py:601`). Athena's (`athena_engine.py:231-303`) and Artemis's (`credit_spread.py:157-221`) versions are the fuller pattern, and they do three things Prometheus's doesn't:

1. **Freeze-limit quantity splitting** — `l_limit = qty_freeze // lot_size`, chunk the requested quantity into broker-legal pieces before placing (`athena_engine.py:238-242`). Verified across all four existing strategies, per the user's own question: Artemis, Athena, and Apollo all implement this chunking, each against a **hardcoded** `QTY_FREEZE=1800` constant in their own `configs.py` (Nifty-specific, since all three trade Nifty/Sensex derivatives). Iris is the outlier — it imports `QTY_FREEZE` (`iris_functions.py:23`) but never actually references it anywhere; no chunking logic exists in Iris despite the import suggesting otherwise. Worth the user knowing that inconsistency exists, independent of anything Prometheus needs.

   **Decided: build this now, not deferred** — per the user's direction ("It's actually basic hygiene in NSE and BSE considering their tight limits... build it. Why wait for later?"). And **Prometheus should not copy the hardcoded-constant pattern** — a better source already exists: `data_pipeline/data/mcx_instrument_master.csv` (already loaded by `resolve_effective_contract()`) carries a `freeze_qty` column per contract, straight from Angel One's own scrip master — confirmed `freeze_qty=10000` for every current CRUDEOILM contract (tokens 565900/580378/569901, `lotsize=10`). Read `self._contract['freeze_qty']` fresh on every run (it's already part of the resolved-contract row, no new lookup) rather than a hardcoded constant — dynamic per-contract, self-updating if MCX ever changes it or a different underlying's freeze quantity differs, which the other four strategies' hardcoded `QTY_FREEZE=1800` can't do.

   **`place_order` returns a *list* of order IDs, not one** — this is the part worth spelling out precisely, since it's a real signature change, not an internal detail contained inside `place_order` alone. Mirroring Athena's shape (`athena_engine.py:238-303`): compute `l_limit = self._contract['freeze_qty'] // LOT_SIZE`, split `lots` into chunks of at most `l_limit` each (`while rem > 0: chunk = min(rem, l_limit); ...`), place each chunk as its *own* `placeOrderFullResponse` call — each independently subject to the rejection-retry and ghost-recovery logic in items 2/3 below — and return the full list of resulting order IDs. Concretely, if `self._contract['freeze_qty']=10000` (`l_limit=1000` lots) and a requested size were ever 1,500 lots, that's two orders: 1,000 + 500. At 15,000 lots, that's fifteen 1,000-lot orders, not one giant rejected order or a naive single split — the `while` loop handles any multiple, not just a boundary case.

   **`get_fill_price_and_qty` needs the matching change — aggregate across the list, not track one ID.** Prometheus's current version (`prometheus_functions.py:768-836`) is built around a single `order_id`: the WS branch does `order_watcher.live_orders.get(str(order_id))`, the REST branch searches `orderBook()` for one matching `orderid`. Both need to become "for every ID in the list, sum filled quantity and value" — Athena's `_fetch_order_details` (`athena_engine.py:305-343`) is the exact reference: WS fast path loops `orderid_list`, accumulating `total_qty`/`total_val` per order and taking the latest `updatetime` as the fill timestamp, then `avg_price = total_val / total_qty`, `filled_lots = total_qty // LOT_SIZE` once all chunks are accounted for (or the poll times out, falling back to REST doing the same aggregation via repeated `orderBook()` lookups). At today's 2-4 lot sizing this list always has exactly one element and the aggregation degenerates to the current single-order behavior — but every call site that currently passes a bare `order_id` string (`_execute_entry`, `_execute_exit_lot`, §7's future combined order) needs to pass/receive a list instead, so this is worth building as the real shape from the start rather than retrofitting once sizing or a freeze-quantity edge case actually exercises it.
2. **Rejection retry** — on an actual `rejected` response (not an exception), retry up to 3 times with a 1s cooldown before giving up and alerting, rather than treating one rejection as final. Applies per chunk, not once per call — a rejection on the 3rd of 15 chunks doesn't invalidate the 2 already placed.
3. **Ghost-order recovery, the important one** — on `DataException`/`NetworkException` specifically (not a blanket catch-all), sleep 2s, then query `obj.orderBook()` and search for a matching order: same symbol, same transaction type, same quantity, status in `complete`/`open`/`validation pending`, updated within the last 60s, and not already claimed by this run's own placed-ID set. If found, that's the real order — recover its `order_id` and proceed to normal fill verification. If not found, the order genuinely never reached the broker and it's safe to retry placement. Also per chunk — Athena's `_placed_order_ids` set (item 3's "not already claimed") is exactly what keeps chunk *N*'s ghost-recovery search from accidentally matching chunk *N-1*'s already-placed order of the same symbol/type/quantity.

**Why this matters more than it looks like on the surface**: Prometheus's `place_order` today treats *any* exception as "definitely nothing happened, safe to retry from scratch." The real failure mode a network blip produces is ambiguous — the broker may have accepted the order and only the *response* was lost. Retrying blindly on that ambiguity risks a genuine double-fill (two real positions instead of one); giving up blindly risks the inverse (a real fill Prometheus never learns about, echoing the shape of the 2026-08-31 incident, just one layer earlier — that incident was about a *lost fill confirmation* on an order Prometheus knew it had placed; this is about not knowing whether the order was placed at all). Ghost recovery is what turns that ambiguity into a fact by asking the broker directly, instead of guessing.

**§7's combined order raises the stakes on this specifically**: a lost response there is worse than today's separate smaller exit/entry orders, because one combined order simultaneously represents *both* the exit and the entry — an unrecovered ghost there has a bigger blast radius than a lost response on just one leg of today's two-order sequence.

**Decided: port Athena's `_place_order`/`_fetch_order_details` pattern (`athena_engine.py:231-343`) into `prometheus_functions.py`'s `place_order`/`get_fill_price_and_qty`**, adapted to Prometheus's simpler single-instrument-token calling convention (no per-leg option-token bookkeeping to carry over, unlike Athena's multi-leg case), and to source the freeze quantity dynamically from `self._contract['freeze_qty']` rather than a hardcoded constant. This is a prerequisite for §7 being genuinely production-ready, and arguably for every other `place_order` call site in Prometheus today, not just the new combined order.

**Status: decided in direction, not yet built.**

## 2. What's simplified: no EOD flatten

- Exit priority drops the EOD-square-off tier entirely — SL → lot1 target → lot2 target → trend_flip only, matching `configs_p3.py`'s calibrated design (backtest has no EOD exit; a production EOD tier would silently diverge from what was calibrated).
- `MIN_ENTRY_TIME` still applies (skip thin opening liquidity). `MAX_ENTRY_BEFORE_CLOSE_MIN` / `LAST_ENTRY_TIME` are **dropped** — `configs_p3.py` never gated entries near close (positional, nothing to "hold until"), and production must match or it trades a different signal than the one calibrated. See §4 for why this isn't quite unconditional — entries still need sequencing around the rollover event specifically.
- **`_teardown()`'s auto-flatten inverts — a default change, not a tweak.** Phase 2 exits any open position at session end, because "always flat by EOD" is the whole invariant the strategy is built on. Phase 3 is the opposite: the position is *expected* to still be open at session end on most days. Teardown's normal path becomes "leave `in_trade`, stop the feed, save state, exit cleanly" — not "exit and go idle." The post-2026-08-31 `exit_confirmed` / "don't force `status='idle'` over an unconfirmed exit" safety logic is preserved unchanged underneath this — it still governs the rare cases Phase 3 *does* need to exit before teardown (SL/target/trend_flip firing right as the loop ends, or a rollover flatten that's still in flight, §6).
- Session-report and Slack copy that currently reads as "stopped, flat" needs auditing — anywhere it implies the day always ends flat needs to instead report "stopped, position left open" as the normal case, not an edge case.

## 3. The new problem: a position can span a contract roll

`resolve_effective_contract()` is called once per session, at `_setup()`, and never re-derived mid-session (`prometheus_functions.py:206-260`'s own docstring: "resolved once ... for the ENTIRE session"). Phase 2 never carries a position past EOD, so whatever this function returns each morning is trivially correct — there's never an open position that could disagree with it. Phase 3 can hold a position for days to weeks (`avg_hold_hours` in the raw backtest ranges 17.9–51.0 across multipliers, max observed 103–145h), so the day the effective contract flips can land in the middle of an open trade.

**Concrete latent bug this exposes if Phase 2's code is reused unchanged**: `_get_ltp()` (`prometheus.py:724-729`) reads the WebSocket feed keyed on `self._contract['token']` (freshly resolved *this session*) but falls back to REST keyed on `self.state.symbol`/`self.state.token` (persisted, possibly the *old* contract) if the feed is down. On a roll day with an open position, **which contract drives the SL/target comparison depends on whether the socket happens to be connected at that tick** — and `state.last_known_ltp` gets written from whichever one answered, contaminating the running trade log and session-report P&L regardless. Meanwhile `_execute_exit_lot` correctly places orders on `self.state.symbol`/`token` — so the actual failure mode isn't "the wrong contract gets traded," it's worse: **a wrong-contract price trips an SL/target trigger, and the exit then fires correctly on the real position, at a price level that meant nothing.** `_setup()`'s subscription set (`self.feed.subscribe_options([self._contract['token']], ...)`) has the same root issue — it only ever subscribes the freshly-resolved contract's feed, never the persisted `state.token`'s, on a resume.

**Fix, stated as an invariant**: **while `status == 'in_trade'`, every price read and every order keys off `state.token`/`state.symbol`; `self._contract` is consulted only while `watching`/entering, and to detect an upcoming roll (§4).** `_execute_entry` already follows this rule. Two call sites need to change to match it: `_get_ltp()`'s WS branch (read `state.token`, not `self._contract['token']`), and `_setup()`'s subscription set (must *also* subscribe `state.token`'s feed when resuming `in_trade`, since it may differ from the freshly-resolved `self._contract`).

## 4. Rollover trigger — proactive lookahead, not reactive discovery

**Mechanism**: each evening, check whether tomorrow's `resolve_effective_contract()` would return a *different* contract than today's `self._contract`. If so, trigger the rollover sequence (§6) tonight, at `ROLLOVER_TIME` — so that by the time tomorrow's fresh `_setup()` runs, state and the freshly-resolved contract already agree.

```python
tomorrow_contract = resolve_effective_contract(SYMBOL, today=next_trading_day)
if tomorrow_contract['token'] != self._contract['token']:
    # trigger rollover tonight
```

This reuses `resolve_effective_contract()` completely unchanged — just called with a forward-dated `today`. No new trading-day-counting logic.

- **"Tomorrow" must be the next *trading* day, not literally `today + 1`.** `resolve_effective_contract`'s own `_count_trading_days_inclusive` already skips weekends when counting days to expiry, but a naive `today + timedelta(days=1)` lookahead only happens to work correctly across a weekend by accident of that separate function's behavior — it should be derived explicitly (walk forward from today using `mcx_holidays.csv`, same source `_count_trading_days_inclusive` already reads, until landing on a day that isn't a full closure) rather than relied on implicitly.
- **This gets the user's "roll a day before the extra margin requirement kicks in" for free, without touching `TENDER_ROLL_TRADING_DAYS=5` at all.** `TENDER_ROLL_TRADING_DAYS` still means exactly what it did in Phase 2 — the last trading day you're allowed to still be on the old contract. By evaluating *tonight* whether *tomorrow* would already be past that boundary, the transition completes before the margin-affected day ever begins. (**Independently verified 2026-09-03, no longer just inherited from Phase 2's stated decision**: Zerodha's support article on this exact topic states MCX charges additional margin on Crude Oil, Crude Oil Mini, Natural Gas, and Natural Gas Mini specifically during "the last 5 trading days before expiry," escalating 5%→25% day by day into expiry — matches `TENDER_ROLL_TRADING_DAYS=5` exactly. A "3 trading days" figure also surfaced during the search, but traced to a different commodity category (base metals' own, shorter tender window per Groww's MCX explainer, which distinguishes gold/silver at 5 days from base metals at 3) — not a competing claim about crude oil specifically. See §16 item 5 for sources.)
- **Entry-ordering rule, new**: the rollover check runs before entry-signal evaluation on every loop tick. On an evening where a roll is about to trigger, suppress fresh and rule-7 entries once `now >= ROLLOVER_TIME` — otherwise a fresh position could open seconds before being flattened straight into a roll.
- `ROLLOVER_TIME` — new config constant, derived the same way Phase 2 derives `EOD_SQUAREOFF_TIME` (`CLOSING_TIME` minus a buffer), same DST-hand-toggle caveat carried over. Under the current DST-in-force `CLOSING_TIME='23:30'` this computes to 23:15, matching what was asked for — but it should be its own named constant, not a reuse of Phase 2's `EOD_SQUAREOFF_TIME` (which doesn't exist as a concept in Phase 3 at all).

## 5. Startup reconciliation — the safety net for a missed rollover [DECIDED 2026-09-03]

`ROLLOVER_TIME` firing correctly depends on the process being alive at 23:15 on that specific evening. It might not be: an MCX holiday, an earlier crash, `KILL` having dropped control, `DISABLE` being set. If the rollover is missed, the next morning's `_setup()` walks straight into §3's problem with an open position on a contract `resolve_effective_contract()` no longer returns.

**`_setup()` needs an explicit check**: if `status == 'in_trade'` and `state.token != self._contract['token']`, that's a missed roll. Two options were weighed:

- **(a) Roll immediately at today's open** — run the full rollover sequence (§6) as part of `_setup()` itself, before arming. Keeps the system self-healing, but means the recalibration math (§8) now has to run against whatever price the new contract opened at, likely a worse moment than a deliberate 23:15 roll.
- **(b) Refuse to arm, alert loudly, wait for manual intervention** — bounded-safe, not indefinitely safe: since the data-pipeline redesign, the old contract keeps getting nightly-refreshed regardless of whether Prometheus itself rolled (front-month selection has no early-roll logic of its own), so the position doesn't go untracked immediately — but past the old contract's *genuine* expiry (not the early tender-roll trigger), `select_front_month_contracts()` drops it and its file freezes, leaving an open position on an expired, no-longer-tracked contract with no data at all.

**Decided: (a).** User's reasoning: this scenario is inherently unlikely — if a trade is open, the algo is almost certainly running (that's what keeps it open in the first place); the case where it *isn't* running with a position still open is one the user would be actively monitoring and would roll manually regardless. (a) is chosen as the automated safety net for the residual case, not because (b)'s bounded-wait framing was wrong.

**Hard prerequisite, confirmed not yet built**: whichever option, §3's invariant ("every price read and every order keys off `state.token`, not `self._contract`, while `in_trade`") must land first. Checked live: `_get_ltp()`'s WS branch (`prometheus.py:726`) still reads `self._contract['token']`, not `state.token` — so *today*, a missed-roll state would monitor SL/target against the wrong contract's price whenever the socket is connected. §3 is not optional scaffolding for this section, it's load-bearing.

## 6. Rollover execution mechanics

1. Flatten the current position (if any) on the old contract, via the existing exit-order/fill-verification machinery (`_execute_exit_lot`/`_execute_exit_all`), new exit reason `'rollover'`. Fully subject to the fill-confirmation invariant — an unconfirmed rollover exit must leave state as `in_trade` on the old contract and retry, exactly like any other unconfirmed exit, not skip ahead to opening the new position regardless.
2. **Re-seed ST and backfill the new contract's history tonight, at rollover time — not deferred to tomorrow's `_setup()`.** The roll now happens the evening *before* the new contract becomes effective, so `seed_st15`/`backfill_contract_if_needed` need to run for the new contract as part of this sequence, not wait for a `_setup()` that won't run until tomorrow.
3. Recalibrate SL/targets for the carried position, if one is being reopened (§8 — decided: historical-basis method, conditional on the ST-disagreement veto).
4. Reopen (or don't — §8) on the new contract, reusing the existing entry order/fill path — **sized to however many lots were actually open at roll time, not blindly both.** If lot1 had already booked its target before the roll and only lot2 was still running, the reopen must request 1 lot per unit, not the `_execute_entry` default of `units * LOTS_PER_LEG * 2`. This is a new correctness requirement (§6 didn't need it before Phase 3, since Phase 2 never carried a partially-scaled-out position across any boundary) — same category of partial-position awareness as `_execute_entry`'s existing `lot1_lots`/`lot2_lots` split (§7), but driven by state read *before* the roll's exit, not by a fill result.
5. Update `self._contract` to the new contract; persist state.

## 7. Rule 7 order placement — combine the flip's exit and re-entry into one net order [DECIDED 2026-09-03]

**Current mechanics, confirmed against the code.** A trend-flip while `in_trade` closes the old position and opens the new one via **three separate broker orders**, not two: `_execute_exit_all` places up to two independent per-lot orders (`_execute_exit_lot(1, ...)`, then `_execute_exit_lot(2, ...)` — `prometheus.py:846-873`), each independently confirmed, and only once `_handle_new_15m_bar` sees the exit fully confirmed closed does it fire a third, independent order via `_execute_entry` for the new direction's full size (`prometheus.py:600-628`). Each order pays its own flat brokerage fee, and each pair of sequential orders has a real (if small) window where the market can move between them.

**Proposal**: since a flip's exit and re-entry are always the same instrument (same token/symbol) just opposite net direction, place **one order for the net quantity** — `old_open_lots + new_trade_lots` — on the new direction's side. Concretely, closing a long and flipping short is just a bigger sell order; the exchange nets it against the existing position automatically, same as any other order. Worked example at the current sizing (`LOTS_PER_LEG=1`, `STATIC_UNITS=1` → 2 lots/trade): both lots of an open long still open, flip to short → one 4-lot sell order (2 closes the long, 2 opens the short). Lot1 already at target, lot2 still open → one 3-lot sell order (1 closes, 2 opens). Both lots already at target (flat) → this degenerates to today's plain entry path, nothing to combine.

**A third degenerate case, symmetric to the one above, surfaced by §17's future filter — not Phase 3 scope, but the sizing logic needs to leave room for it now.** This whole proposal assumes a flip is *always* both an exit and a re-entry together — true in Phase 3 (no filter exists), not necessarily true once §17's 1h-alignment filter exists: the 15m flip can still invalidate the old position (exit is unconditional) while the counter-direction re-entry gets blocked (filter disagrees). That's not "skip a downstream `_execute_entry` call" the way it looked in §17's first pass — it changes the **combined order's own requested quantity**, since the order is sized once, up front, before it's placed. `new_trade_lots` must be computed as zero whenever re-entry isn't going to be allowed, collapsing the order to `old_open_lots` only (a plain exit, no netting into a new position) — the mirror image of the already-documented "both lots flat → entry-only, nothing to combine" case. **Nothing to build for this in Phase 3** (the gate that would ever set `new_trade_lots = 0` doesn't exist yet), but whoever builds §7 should compute `new_trade_lots` as its own explicit step — not hardcode it as "always `old_open_lots`'s twin" — so Phase 4 has a single place to hang the filter later instead of restructuring this section's order-sizing logic from scratch. Partial-fill reconciliation is unaffected either way: an exit-only order reuses the ordinary single-purpose exit-fill path, no entry-side split to reconcile at all — simpler than the combined case, not harder.

**This is not only a cost optimization — it removes a whole failure class by construction.** `_execute_exit_all`'s gate on `closed` before ever calling `_execute_entry` (`prometheus.py:619-623`) exists because of the 2026-08-31 incident: two *independent* orders can desynchronize (exit fails silently, entry fires anyway, real position and recorded state disagree on which direction is held). A single order against a single instrument cannot produce that failure mode — there is exactly one fill event, and `net_position_before + signed_filled_qty = net_position_after` is unambiguous regardless of how much of the order actually filled. The two-step confirm-then-fire gate exists to manage risk *between* two orders; with one order, that specific risk doesn't exist to manage.

**The real new work: partial-fill reconciliation.** If the combined order doesn't fill completely, the code needs to know how much closed the old position vs. opened the new one. This is genuinely new logic, but it's an extension of a pattern already in this file, not a foreign one — `_execute_entry` already splits one fill across `lot1_lots`/`lot2_lots` post-hoc (`prometheus.py:661-668`, `lot1_lots = min(filled_lots, units*LOTS_PER_LEG); lot2_lots = max(0, filled_lots - lot1_lots)`) for exactly this reason on the entry side alone. Extended to a combined order:
- `closed_qty = min(filled, old_open_lots)` — finalizes the old trade's remaining lot(s) at the fill price. **Tie-break, DECIDED: absorb lot2's remainder before lot1's** (the opposite of what this section originally proposed, which had defaulted to lot1-first purely by analogy to `_execute_exit_all`'s existing lot1-then-lot2 order — not actually re-examined for this new context until now). User's reasoning: lot1 carries the nearer target; if a partial fill leaves one lot stuck open on the stale direction and the market then reverses back in that stale direction's favor (the position's original, pre-flip direction), keeping lot1 (not lot2) as the one still open means it's the nearer, faster-hitting target that resolves it — the position exits sooner in that recovery scenario. So lot2 is what gets attributed as closed first.
- `max(0, filled - old_open_lots)` — feeds directly into the existing entry partial-fill logic above, unchanged, for the new trade.
- **Retry mechanism, DECIDED — corrects a wrong claim this section originally made.** The original draft asserted a stuck partial exit would "retry on the next tick, same as any other unconfirmed exit today" — checked against the code and that's false: `_handle_new_15m_bar`'s Rule 7 branch only fires when `bar['trend_flip']` is `True` **and** `direction_now != state.direction` (`prometheus.py:610`); `trend_flip` is a one-shot transition flag, true only on the bar where the flip actually happens, so a still-stale `state.direction` on any *later* boundary no longer re-triggers anything — `_check_exit_conditions_ltp` (the continuous 500ms in-trade loop) doesn't cover this case either, since it only checks SL/target against the *current* `state.direction`. Confirmed: as written, a partially-resolved Rule 7 flip would sit stuck indefinitely with only the original alert ever firing.
  - **Fix**: if `filled < old_open_lots` (including the `place_order()`-returns-no-`order_id` case below, which is `filled=0` by definition), set a `_pending_flip` marker on state (direction, signal price/ts, remaining lots to close/open) instead of just logging and returning. Re-attempt the combined order on **every tick** of the existing 500ms in-trade loop (not gated on a fresh 15-min `trend_flip` transition) until it fully resolves — same non-blocking philosophy as `_pending_recovery` for missed candle windows elsewhere in this file.
  - **Alerting**: fire the CRITICAL `#error-alerts` immediately when `_pending_flip` is first set, then a debounced re-alert while it stays stuck — reuse the stale-tick-watchdog's existing 5-minute debounce convention (§0/README) rather than inventing a new cadence, so a genuinely stuck position doesn't get silently retried forever with no further visibility, but also doesn't spam Slack every tick.
  - Clear `_pending_flip` once the combined order fully resolves (old position closed, new one opened per the sizing rules above).
- The fill-confirmation invariant carries over unchanged: never fabricate a price for the unfilled portion, never guess — whatever the broker didn't confirm stays exactly as it was before the order.
- **Named explicitly, not left implied**: if `place_order()` itself returns no `order_id` for the combined order (the exact 2026-08-31 failure mode — `placeOrderFullResponse` returning `data.orderid=None`), that's `filled=0` by definition — nothing closes, nothing opens, the old position (if any) is untouched, feeds into the same `_pending_flip` retry-until-resolved path above. Once §1's ghost-recovery is built, most connectivity-driven instances of this should self-resolve *inside* `place_order()` before ever reaching this fallback; `_pending_flip` exists for what's left over — a genuine rejection or a genuine partial fill, neither of which §1 can retry away on its own. A single combined order is arguably *more* robust against a repeat of this specific incident than today's two-function split: the 2026-08-31 root cause was `_execute_entry` having a no-`order_id` guard while `_execute_exit_lot` didn't — two functions independently (and inconsistently) defended. One function, one `place_order()` call, one guard to get right removes the place that inconsistency lived.

**One accuracy upside worth naming**: using a single fill price for both the old trade's exit and the new trade's entry (when the order fills at one clean price, or a single blended average across partial fills) is *more* accurate than today's two-sequential-orders approach, not less — it's literally the same execution moment, whereas today's separate exit-then-entry has a real window for the market to move between them.

**Excluded at the rollover boundary, as the user identified**: old and new legs there are on *different* tokens/symbols (expiring vs. far-month contract) — the exchange has no way to net a sell of one instrument against a buy of another, so §6's rollover-flatten-then-reopen stays two separate orders. This section only applies to a flip on an already-effective, non-rolling contract.

**Status: decided in direction, not yet built.** Same production-QC weight as §15 (Prometheus write-removal) — live-trading order-execution code, not yet live-tested even under `DRY_RUN=True`. Depends on §1 (ghost-order recovery) landing first, per §1's own note.

## 8. SL/target recalibration [DECIDED 2026-09-03]

**Proposed method** (as described): look up what the *new* contract was trading at, at the *same historical timestamp* the original entry happened on the *old* contract. Use that price as the basis, and reapply the calibrated `SL_PCT`/`TARGET1_PCT`/`TARGET2_FLAT_PCT` formulas against it, exactly as if it had been the entry price all along.

**What this assumes, precisely**: if the calendar spread between the two contracts (old price minus new price) has stayed roughly constant between the original entry date and the rollover date, this exactly preserves the trade's progress-so-far — the new contract's current price minus this historical basis equals the same point-move the old contract actually experienced. If the spread has drifted, the recalibrated distance-to-target is off by however much it drifted, silently.

**Check #1, run 2026-09-03 — straddling rolls are common, not rare, overturning this section's original hedge.** Cross-referenced each `bespoke_trade_summary.csv` entry/exit timestamp against every CRUDEOILM contract's actual rollover date (`TENDER_ROLL_TRADING_DAYS=5` trading days before expiry, computed with the same `_count_trading_days_inclusive` logic + `mcx_holidays.csv` the production code uses, across all 9 contracts on disk, Feb–Oct 2026):

| | Total trades | Straddle a rollover | Frequency |
|---|---|---|---|
| mult_2.0 | 375 | 7 | ~78% of the 9 rollovers in the backtest window |
| mult_2.5 | 283 | 3 | ~33% of the 9 rollovers |

The plan originally guessed "rare — a couple of instances," reasoning from the *unmanaged* raw-backtest hold time. The real, lot-managed figure is the opposite: a position sits open across the roll on most contract cycles at mult_2.0, and a third of them even at the more conservative mult_2.5. This was a real correction to the plan's own assumption, not a rubber-stamp of it.

**Check #2, basis drift vs. target distance — still blocked, decided to proceed anyway.** `TENDER_ROLL_TRADING_DAYS=5` off the Aug-19 expiry puts a real rollover at **2026-08-12, 23:15** (confirmed against `_count_trading_days_inclusive` and the real MCX holiday calendar), and both mult 2.0 and mult 2.5's bespoke backtests had a position open at exactly that moment (trade 344 / trade 264, both bearish, both lots still open). Tried computing the basis directly from this instance and hit a data problem, not a market one: `2026-09-21_futures.csv`'s price is an **exact clone** of whichever contract was genuinely front-month at each point in its backfilled history — checked against August (its own eventual predecessor), July, and June, all three showing **zero spread across the entire overlap, to the last paisa, over ~18-19k one-minute bars each**. Ruled out our own code as the cause (`download_futures_contract` correctly requests the contract's own token from AngelOne); the clone is coming from the broker's historical response for a token that far from expiry. Confirmed with the user this reads as a broker/historical-API artifact, not a genuine MCX quoting convention — i.e., a *live* LTP poll for the next contract at the time would likely be genuine; it's specifically a *retroactive historical* request for an inactive token that comes back corrupted. **This means check #2 cannot be run against current historical data at all**, and can only be redone once genuine live-captured history has accumulated (see the prerequisite below) — which will take months, not something to wait on.

**Decided: historical-basis method (option 1), accepting check #2's risk unvalidated.** User's explicit call, made with full knowledge that check #2 is blocked and basis drift is unverified — including the acknowledged possibility that this basis-preservation approach is effectively financing whatever arbitrage activity keeps the two contracts' spread in line, a cost accepted as the price of capital-efficient roll behavior rather than something to design around further. Revisit once check #2 is actually runnable; nothing about the design below needs to change to switch methods later, it's a config-level swap, not a rebuild.

**Three build requirements attached to this decision, all explicit, none optional:**

1. **Partial-lot rollover sizing and target assignment.** If only one lot survives to the rollover (lot1 already closed at its original target, lot2 still open), the reopened position on the new contract is sized to 1 lot per unit (§6, already decided) — and that lot's target is computed using the **lot2 target formula** (`TARGET2_MODE`/`TARGET2_FLAT_PCT`), off the recalibrated entry price, not lot1's. The surviving lot was always the "lot2 position" continuing toward the farther target; after the roll it keeps behaving that way, rather than restarting as a fresh lot1. If both lots survive, reopen 2 lots with both `lot1_target`/`lot2_target` recalculated normally off the recalibrated entry price, same as any fresh entry.
2. **Actual fill price and recalibrated basis price are two different numbers — both need to exist as separate fields, and each downstream use needs to read the right one.** The reopened position's real fill price (used for genuine P&L against real money paid) will differ from the historical-basis price used to compute where `sl_price`/`lot1_target`/`lot2_target` sit. Add a new state/log field (e.g. `recalibration_basis_price`) distinct from `entry_price`: SL/target *levels* get computed once, at reopen time, off the basis price (same as any entry, just with a different source price) and then persist as ordinary absolute levels — `_check_exit_conditions_ltp` doesn't need to know about the distinction afterward, since it only ever compares live LTP against the already-computed `sl_price`/targets. P&L (`_finalize_trade`, the trade log's `lot*_pnl_points`/`lot*_pnl_rs`) must compute off the real `entry_price`, never the basis price. Cheap to add (new columns/fields, per user), but must be threaded through correctly at the one place it's computed (reopen) and the two places it's consumed (SL/target math vs. P&L math) — get either one wrong and either the P&L or the exit levels are silently off.
3. **ST-disagreement veto — historical-basis carrying is conditional, not unconditional.** After §6 step 2 re-seeds the new contract's ST fresh, compare its current computed trend direction against `state.direction` (the direction being carried). If they **agree**, proceed with historical-basis recalibration and reopen as above. If they **disagree** — old contract bullish, new contract already bearish, or vice versa — do not reopen at all: exit the old position normally (`exit_reason='rollover'`) and go to `watching` on the new contract, waiting for a genuine fresh flip, exactly like the flatten-and-don't-reopen case. This directly resolves the coherence risk flagged below (a freshly-seeded trend disagreeing with the carried direction, with no flip-transition to ever surface it) by only ever carrying the position when the two contracts' trends actually agree at the moment of the roll. Slots naturally into §9's existing schema — this is exactly the "rolled-and-not-reopened" case already covered there (one row, no second leg).

**New prerequisite this surfaced, specific to the historical-basis method — now partially built (2026-09-02).** At the time this was written, nothing in the pipeline ever captured live price data for a contract before it became front-month: `select_front_month_contracts()` (used by both `data_downloader_mcx.py`'s offline backfill and `mcx_live_downloader.py`'s live poller) returned exactly one row per underlying, and `resolve_effective_contract()` resolved to that same single contract — so the only way to learn what the next contract was trading at some point in the past was a historical backfill request after the fact, the exact request type just shown to come back corrupted.

`data_downloader_mcx.py` now also tracks the **next-month** contract for every enabled underlying, including CRUDEOIL/CRUDEOILM (`select_next_month_contracts()` — second-nearest unexpired expiry, downloaded via the same `download_futures_contract()` path, forward-only from first sight, same as front-month; initially scoped to just the traded pair via a `track_next_month` config column, simplified 2026-09-02 to apply uniformly to all 22 enabled underlyings instead, alongside a wider redesign — see below). Run nightly (`run_mcx_downloader.sh`, weekdays 23:56 IST, right after the session closes), this means genuine live-captured history now accumulates on the next contract for however long it sits at next-month before rolling — which is exactly what check #2 above needs, and directly closes the "no genuine live-captured history exists" half of this prerequisite.

What this does *not* yet close: the history only starts accumulating from 2026-09-02 forward (no backfill, by design — see the LOOKBACK_DAYS section of `data_pipeline/README.md`), so check #2 still can't be run against the 2026-08-12 rollover instance above — that gap in the data predates this fix and can't be recovered. It also doesn't retroactively fix the already-corrupted `2026-09-21_futures.csv`/etc. on-disk files described above; those stay corrupted (`data_pipeline/README.md`'s "Known limitation, not yet cleaned up"). Whether the accumulated next-month history by *some future* rollover is enough — or whether "started early enough (ideally from first listing)" needs a deeper fix — remains open; re-evaluate once a rollover happens after 2026-09-02 with a real open position at the time.

**Reset-to-now, the other alternative originally weighed here, is dropped.** It has no basis-drift risk, but it doesn't solve the ST-coherence problem either (it also carries the position onto the new contract's freshly-seeded trend, same as historical-basis) — so it would have taken on one of the two risks for none of the benefit (discarding real trade progress) that made historical-basis worth the drift risk in the first place. Flatten-and-don't-reopen isn't a competing alternative anymore either — it's now the built-in fallback specifically for when requirement 3 above (the ST-disagreement veto) fires, not a separate top-level choice.

## 9. Trade-log schema — rolled trades need explicit representation [DECIDED 2026-09-03]

`prometheus_trades.csv` and `trade_summary_p2.csv` share an identical schema today: one row per trade, `lot1_*`/`lot2_*` as columns (not rows) for the two-lot scale-out, `exit_reason` a free string (not an enum — confirmed live, costs nothing to add a new value). Neither file has any concept of a rollover; the question is which axis a roll should split on.

**Decided: two linked rows**, joined by a new nullable `parent_trade_id` column. A roll produces a second `trade_id` row: the old-contract row closes exactly as any trade does today (lot columns filled in as usual; whichever lot didn't already hit target closes with `exit_reason='rollover'`), and the new-contract row is an ordinary fresh trade row except `parent_trade_id` points at the old row's `trade_id`. This costs one new column and changes nothing about what a row or a lot1/lot2 column already means — the alternative (folding both contracts' lot data into one row) would have needed a third splitting dimension inside a single row, or would have thrown away the old leg's own entry/exit/P&L detail to fit the existing lot1/lot2 slots.

This shape covers all three real cases without distortion: never-rolled (today's row, untouched), rolled-and-reopened (two rows, chained via `parent_trade_id`), and rolled-and-not-reopened — e.g. if §8 picks flatten-and-don't-reopen — which is just one row with a `rollover` exit reason and no second row at all, since nothing reopened.

**Also decided**: `direction` gains two new values, `bullish-rollover` / `bearish-rollover`, used only in the trade-log row for a roll-continuation entry (the new-contract row) so a roll is visible at a glance without cross-referencing `parent_trade_id`. **Implementation note**: `state.direction` itself must stay the plain `'bullish'`/`'bearish'` binary everywhere it drives real logic (`_execute_entry`'s `'BUY' if direction == 'bullish' else 'SELL'`, the Slack report's P&L-sign calc) — the `-rollover` suffix is substituted only at the trade-log row-write call site for that one row, never assigned into `state.direction`.

Consumers doing a naive `sum(total_pnl_rs)` over `prometheus_trades.csv` will double-count a rolled trade's continuation as a second trade unless they group by `parent_trade_id` — documented as a schema convention, not solved structurally (same category of thing every reader of this file already has to know, like which columns are lot1 vs lot2).

## 10. First-minute exit guard — avoid SL/target/trend_flip on session-open price-discovery noise

**Real incident, 2026-09-02**: CRUDEOILM's very first 1-min candle of the day (09:00:00) printed O=8199 / H=8627 / L=8180 / C=8605 — a 447-point (5.45%) high-low range inside a single minute, on real volume (201 contracts), not a stray tick. User-reported (not independently verified against a file in this repo — the local `CRUDEOIL` data only runs to 2026-08-28, no 09-01/09-02 coverage): the full-size CRUDEOIL contract's same minute showed a normal ~10-point range (8603/8611/8601/8604), suggesting this was thin-liquidity price discovery specific to the mini contract's first minute rather than a genuine underlying move — plausible and consistent with everything below, but flagged here as user-reported pending independent confirmation once CRUDEOIL data for these dates is available locally. Prometheus was flat at the time (last position had closed the evening before), so nothing fired — but this is exactly the shape of print that could trigger a spurious SL or target exit on a real open position, and Phase 3 makes that the *normal* case, not a rare one: positions now routinely sit open across a session's opening bar (§3), where Phase 2 almost never did (always flat by EOD, so its exit-check logic essentially never runs at session start — except in the rare case of a genuinely unconfirmed EOD-exit failure carrying a position into the next day, per the post-2026-08-31 fill-confirmation invariant).

**Precedent already in this codebase**: Apollo has exactly this guard. `apollo_configs.py`: `NO_EXIT_BEFORE = '09:16'`, with the comment "No exit on 09:15 candle close — defer SL check to 09:16." Applied as a plain, non-blocking early return at the top of both exit-check functions (`apollo.py:920-922`, `:942-944`): `if datetime.now().time() < self._no_exit_time: return False`. Artemis has a heavier version (`credit_spread.py:948-991`) that blocks with `sleep()` until 9:16 and does a single fresh re-check when an SL condition fires early, rather than just skipping. Apollo's version is the right fit here — Prometheus's own loop already re-ticks every 0.5–1s, so the very next tick after the guard time re-evaluates with a fresh price automatically; no explicit sleep needed.

**Requirement**: add `NO_EXIT_BEFORE` to `prometheus_configs.py`'s production counterpart, set to **09:01** — one minute past MCX's actual session open (`SESSION_START_TIME='09:00'`), mirroring the *same principle* Apollo/Artemis apply at NSE's 9:15 open (one minute of price-discovery buffer), not the literal clock value, since MCX opens 15 minutes earlier than NSE. Gate the continuous LTP-driven SL/target checks (`_check_exit_conditions_ltp`) behind it.

**This guard does NOT cover trend_flip — a real gap, not a simplification.** Checked `_handle_new_15m_bar` (`prometheus.py:551-628`) directly: it runs unconditionally on every 15-min boundary, with no time gate anywhere in it. It builds the new bar, calls `compute_st` on the combined series, persists it, and reads `flip`/`direction_now` straight off the just-recomputed trend — completely independent of `NO_EXIT_BEFORE`, which only guards the separate continuous-LTP check path. A corrupted 09:00 bar that happened to also cross the existing ST band would have produced a *recorded* `trend_flip`, and under Rule 7 that's simultaneously an exit and a reversed entry, fired immediately at 09:15:04-ish when the bar closes — `NO_EXIT_BEFORE` would not have stopped it. §11 below covers this properly, since it's really the same underlying problem (one bad print distorting the signal) rather than a second, separate first-minute issue.

## 11. Price-artifact protection for ST_15 — a single bad print can freeze the signal, not just trigger one bad exit

**The same 2026-09-02 candle corrupted the Supertrend calculation itself, not just the momentary price.** Computed `compute_st` directly against real CRUDEOILM data across the anomalous bar, both multipliers:

- **Mult 3.0: completely frozen.** ST = 8410.370081 at 23:15 (the bar before), stays at *exactly* 8410.370081 through 09:00 (the anomalous bar), 09:15, and 09:30 — three consecutive 15-min bars, 45 minutes, zero movement, while price rallied from ~8528 to ~8617.
- **Mult 2.0: frozen during the bad bar, then a muted creep.** ST = 8452.246721 at 23:15 and stays there through 09:00, then only creeps to 8456.50 (09:15) and 8472.75 (09:30) — far slower than the move in price would suggest.

**Mechanism**: Supertrend's ratchet takes `max(previous_lower_band, basic_lower)` in an uptrend, where `basic_lower = midpoint − multiplier × ATR`. The 447-point true range on that one bar spiked ATR, which pushed `basic_lower` *down* — below the already-ratcheted previous value — so the ratchet just kept the old band unchanged. The close (8606) itself was fine; it's the *range* that corrupted ATR, and ATR's own rolling window then carries that one inflated reading forward for roughly `ST_PERIOD` (10) more bars, not just this one — meaning the signal can stay distorted well past the bad print itself, not just risk one bad immediate trigger. This is a different, more fundamental problem than §10: §10 stops the SL/target *action*; this is the *signal itself* being wrong for an extended window afterward, including the trend/flip state that Rule 7 acts on.

**Before assuming this is fixable by filtering at all, checked whether the artifact is distinguishable from genuine volatility by size.** Computed the full 15-min true-range distribution across CRUDEOILM's whole history (8,574 bars, mean 48.9, std 43.8). Today's 447-point bar ranks **#11 largest, 99.87th percentile, ~9.1 std devs above the mean** — large, but **not uniquely so**: at least 10 historical bars are equal or bigger, up to 809 points (2026-03-09). **Pure magnitude alone can't separate "bad print" from "real large move"** — but cross-checking each of those 10 bars against CRUDEOIL (the full-size contract, same underlying, same exchange, same minute) at the same timestamps found a much cleaner signal than magnitude:

Today's incident is the **sixth** confirmed instance of this exact pattern over ~7 months, not a one-off.

**2026-03-09's opening bar (ratio 0.70) is excluded from that pattern, not a partial exception to it.** User's own external research: that date had MCX-side backend changes that may have corrupted data independent of anything about price discovery — a separate, unrelated data-quality issue, not a milder version of the same artifact. Whatever caused it is out of scope here; it shouldn't be forced into the "opening bar" story just because it happened to also be an opening bar, and it shouldn't inform the fix below (its data is potentially unreliable on both instruments, so CRUDEOIL isn't a trustworthy reference for that specific date either).

**Decided: cross-instrument substitution, not filtering.** Since all six confirmed artifacts land in the same single bar (09:00, the very first candle of the session) and CRUDEOIL is confirmed reliable at that exact moment every time, the fix doesn't need to guess at a magnitude threshold or discard information — it can directly replace the bad print with a known-good one. Runs once per session, right after the 09:00 candle downloads; no comparison for any other bar, any other time:

```python
def patch_opening_bar_if_artifact(m_bar: dict, o_bar: dict, threshold: float = 0.5) -> dict:
    """
    m_bar/o_bar: the 09:00 1-min candle for CRUDEOILM/CRUDEOIL, each
    {'open','high','low','close'}. Same underlying, same per-barrel price
    (only lot size differs -- no scaling needed, see prometheus_backtest/
    README.md's CRUDEOIL cross-validation convention). If CRUDEOIL's true
    range is under `threshold` of CRUDEOILM's at this exact minute,
    CRUDEOILM's own print is thin-liquidity noise -- substitute CRUDEOIL's
    OHLC outright. Runs once, right after the 09:00 candle downloads; BAU
    for the rest of the session either way.
    """
    m_tr = m_bar['high'] - m_bar['low']
    o_tr = o_bar['high'] - o_bar['low']
    if m_tr > 0 and (o_tr / m_tr) < threshold:
        logger.warning(f"Opening-bar artifact: CRUDEOILM TR={m_tr} vs CRUDEOIL "
                        f"TR={o_tr} (ratio {o_tr/m_tr:.2f}) -- substituting.")
        return o_bar.copy()
    return m_bar
```

`threshold=0.5` is a deliberate, evidence-backed choice: it clears every confirmed artifact (0.04–0.38, all comfortably below) with margin, and sits below every confirmed real-move ratio (0.88 and up) from the non-opening-bar evidence — a clean gap, not a fitted cutoff. Because the check only ever runs against the 09:00 bar, it never touches 2026-04-08's 09:30 bar (ratio 0.50, ambiguous, but out of scope by construction) or 2026-03-09's excluded case.

**Implementation constraint, pinned down explicitly for §17's forward compatibility (not a new decision, just a precision requirement on this one):** `patch_opening_bar_if_artifact()` must patch the candle **in `self._df_1m_today` itself, at 1-min-ingestion time** — before it's read by *any* resample, not inside the 15m-specific bar-builder. Every derived timeframe reads from the same raw 1-min series; a future 1h resample (§17) hits the exact same corrupted 09:00 print, for the exact same reason, if it ever includes that bar in its own ATR window. Patching the canonical 1-min series once means any future timeframe inherits the fix automatically — patching it only inside `_handle_new_15m_bar`'s own bar-building step would silently leave a future 1h series unprotected, re-discovering this same incident a second time.

**This beats both insertion points considered earlier** (1-min raw clamp, and ATR-input winsorizing): it doesn't rewrite broad swaths of history the way a general clamp would (only ever touches one candle, once a day, and only when the check actually fires), and it doesn't need a guessed cap or a discarded bar the way winsorizing/exclusion would — CRUDEOIL's own print *is* the correct value, not an estimate of one.

**New production requirement this creates**: the pipeline needs CRUDEOIL's own 09:00 candle available at the moment CRUDEOILM's downloads, every session — a live poll for that one instrument, once a day, right at the open. Smaller and more targeted than §8's "track every listed contract continuously" requirement (that one's for arbitrary historical lookback across a rollover's whole holding period; this one only ever needs a single, same-day candle), but it's the same class of gap — nothing in the current pipeline polls CRUDEOIL at all today (`select_front_month_contracts` per underlying, §8) — so this still needs building, not assuming.

**Applies to both backtest and production, but not identically implemented**: the backtest correction (`prometheus_backtest/data_loader.py`, `_CRUDEOILM_OPENING_BAR_CORRECTIONS`) is a hardcoded dict of the 6 confirmed dates and their known-correct OHLC values — a fixed, reviewed substitution for reproducing this calibration, not a live `threshold=0.5` check. It does not auto-detect a 7th instance if one occurs in data added later; a future date showing the same pattern needs to be confirmed and added to the dict by hand, the same way these 6 were. Production runs the actual live `patch_opening_bar_if_artifact()` check described above, every session, against whatever CRUDEOIL prints that day — that one *is* general-purpose. Don't assume the backtest's behavior generalizes past these 6 dates.

**Cost of getting this wrong either way**: this changes the ST_15 series again, which means the mult 2.0-vs-2.5 comparison (already re-run once this session for the weekend-bar fix) needs re-running a second time once this is implemented. Known cost, not a surprise.

## 12. 15-minute-boundary REST failure can silently build a wrong (or permanently missing-flip) ST_15 bar [DECIDED 2026-09-03]

**The mechanism, confirmed against the code, not hypothetical.** The 1-min REST poller (§4) retries a failed `getCandleData` call 3 times, 1 second apart (`INNER_RETRY_ATTEMPTS=3`, `INNER_RETRY_INTERVAL_SEC=1`), then gives up and defers the window to `_pending_recovery` — deliberately non-blocking, so a stretch of AB1021 failures never stalls the LTP-driven exit-check loop (§4's "candle- vs LTP-dependent logic stay two explicit blocks" requirement). This is the right design for every *other* minute. At a 15-min boundary specifically, `run()` calls `_handle_new_15m_bar(boundary)` **unconditionally**, immediately after that boundary's own fetch attempt — whether or not the fetch actually succeeded (`prometheus.py:475-487`). If it failed, `_handle_new_15m_bar` builds the bar from whatever `self._df_1m_today` already has, missing the tail minute(s). The existing "`<8` of 15 rows" incomplete-data warning does not catch a merely-short tail (14/15 present triggers nothing) — a wrong `close` goes into `compute_st` silently, no log line at all.

**Worse than a delayed signal — it's a bar that never self-corrects.** Once `_recover_pending_windows()` fills the missing window on a later cycle, nothing re-triggers a recompute of the 15m bar that was already built without it: `_handle_new_15m_bar` only ever appends a *new* bar at the *next* 15-min mark, keyed on that mark's own `window_start` — it never revisits an earlier timestamp. So a boundary hit by an AB1021 stretch doesn't just see its flip a minute late; that slot's close/ST is **wrong for the rest of the session**, until a restart's `seed_st15` recomputes from the by-then-corrected on-disk file. A genuine trend_flip masked by the wrong close is missed outright, not delayed.

**Two fixes, doing different jobs — both wanted, not a choice between them:**

1. **Primary defense: decouple "boundary reached" from "compute the bar."** Instead of firing `_handle_new_15m_bar` unconditionally at the boundary tick, only fire it once `self._df_1m_today` genuinely has all 15 minutes for that window — checked on each subsequent 1-min cycle, reusing the `_recover_pending_windows()` call that already runs every cycle regardless. This achieves "keep trying longer" without ever blocking the exit-check loop (a literal blocking retry at the boundary was considered and rejected — see below). **Cutoff, DECIDED: 1 minute.** The wait itself doesn't put an open position at risk — `_check_exit_conditions_ltp` (SL/target) keeps running every tick throughout, completely unaffected by the wait — so the real cost of the cutoff is purely how long flip detection (Rule 7, fresh entries) can lag the true boundary. User's call: minimize that lag over minimizing use of fix #2's fallback, since a missed/delayed flip matters more than a few minutes of slightly-less-precise OHLC reconstruction. This also happens to line up with the one confirmed live data point (2026-09-03: 11:51's burst failed all 3 attempts, 11:52's succeeded — a 1-minute cutoff would have just caught that recovery). If the cutoff is hit, fall back to fix #2 or, failing that, build from whatever's on hand with a loud (not silent) warning — matching the spirit of the existing `<8` check, extended to also fire on "boundary passed, window still short."
2. **Fallback bridge: a local, Prometheus-only LTP sample buffer**, used only once fix #1's cutoff is hit and a bar still has to be built with something better than a hole. Confirmed nothing stores tick history anywhere today — `websocket_feed.py`'s `SharedFeed._ltp` is `{token: float}`, overwritten on every tick; `_get_ltp()` only ever reads the *current* value. A true tick-accurate reconstruction would need a per-tick callback added to `SharedFeed` itself — shared infra with blast radius on Apollo/Athena/Artemis/Iris, the same caution already on record elsewhere in this repo for that file (e.g. the unexplained `SmartWebSocketV2._on_close()` shutdown anomaly, deliberately left unpatched there for the same reason). Avoid that: instead, have Prometheus poll `feed.get_ltp()` locally every cycle (currently only polled while `in_trade`; extend to always), keep a small bounded local buffer (~20-30 min is plenty), and use *that* — not genuine ticks, ~1Hz-sampled LTP — to patch a boundary window's OHLC when REST is still short past the cutoff. Explicit, accepted limitation: 1Hz sampling can miss a fast intra-second spike between polls, so the reconstructed high/low is approximate, not exact. Fine for a rare fallback patch; not proposed as a replacement for REST-sourced candles, which stay authoritative once they arrive (the local buffer is never written to disk or treated as a second source of truth — patches this one in-memory bar only).

**Why not just retry longer, synchronously, at the boundary** (the simpler version of fix #1 first considered): rejected. It reopens exactly the problem §4's non-blocking design exists to avoid. Given AB1021 failures can span multiple consecutive minute-cycles (confirmed above, not a worst-case guess), a blocking wait "long enough" to ride that out could stall LTP-driven SL/target monitoring on a live position for the better part of a minute — worse than a wrong bar, since it risks missing a real exit entirely rather than mis-timing a signal.

**Status: decided, not yet built.** Same production-QC weight as §15 (Prometheus write-removal) — this is live-trading signal-integrity code, not yet live-tested even under `DRY_RUN=True`.

**Does NOT generalize to §17's future 1h timeframe for free — flagged so nobody assumes it does.** Unlike §11/§14's fixes (which patch the raw 1-min series upstream of any resample), this fix is boundary-size-specific: it checks for 15 genuine minutes of data at a 15-min mark. A future `_handle_new_1h_bar` would need its own analogous-but-separate deferred-computation gate, checking for 60 minutes, with its own cutoff decided against 1h's own flip-detection-lag-vs-precision tradeoff — not necessarily 1 minute, and not something Phase 4 can just inherit. Worth building that as a parallel mechanism when the time comes, not a shared one.

## 13. Reporting: realised, unrealised, and total P&L in trade updates

**Requirement (Phase 3 only — Phase 2 keeps its current reporting unchanged):** every periodic trade update and the "still open at session end" line in the session report must show realised P&L, unrealised P&L, and their total, not unrealised alone.

**Why Phase 2 doesn't need this and Phase 3 does:** in Phase 2 a position is open for at most one session, so the brief window where lot1 is booked and lot2 is still running is transitional — the trade finishes and its true total lands in the session report within the same day regardless. In Phase 3 a position can run for days to weeks (§3), so "lot1 booked, lot2 still open" isn't a brief transitional state — it's the normal shape of a trade for most of its life. Reporting only the open lot's mark-to-market during that whole stretch hides the majority of what's actually locked in.

**This is also a real, currently-existing gap, not just a missing feature — worth fixing precisely because of what it's currently silently dropping:**

- `_send_trade_update()` (`prometheus.py:941-956`) computes P&L only from `lots_open` — whichever of lot1/lot2 still has `status == 'open'`. Once a lot books, its P&L disappears from every subsequent update; there's no realised term at all.
- `_send_session_report()`'s "still open" fallback block (`prometheus.py:414-429`) has the same shape: it computes one `pnl_pts`/`pnl_rs` off `lots_open` only, and labels the whole thing `_(unrealised)_`. A trade that has lot1 already booked and lot2 still running never gets appended to `prometheus_trades.csv` — `_finalize_trade()` only fires once *both* lots are closed (`prometheus.py:763-764`) — so `trades_today` never picks up lot1's locked-in P&L either. **The already-realised portion of a still-open trade is currently invisible in both places it could show up**, and `total_rs` (the session-report grand total) silently understates by exactly that amount whenever a trade is mid-way through its scale-out at report time.

**Fix, both call sites**: compute per-lot realised P&L from whichever of `lot1_exit_price`/`lot2_exit_price` is populated (lot status not in `{'open', 'never_opened'}`) against `entry_price`, direction-signed, times that lot's filled quantity — this is already exactly what `_finalize_trade()` computes per lot, just needed earlier and un-conditioned on both lots being closed. Compute unrealised P&L the same way the current code does, but only over lots still `status == 'open'`. Report all three:

```
Realised   : <sum of booked lots' pnl>
Unrealised : <mark-to-market of still-open lots at current LTP>
Total      : <realised + unrealised>
```

**Interacts with §9's trade-log-schema decision — [DECIDED 2026-09-03]: no carry-forward.** A rolled position's two legs are treated as genuinely separate trades, matching §9's two-linked-rows schema and the new `bullish-rollover`/`bearish-rollover` direction labels: the old leg closes normally (`exit_reason='rollover'`, its own realised P&L booked and logged on its own row, nothing further to do with it), and the new leg starts clean — `state.direction`, realised, unrealised all reset exactly as they do for any fresh trade, with no `carried_realised_rs` or equivalent needed. The new leg will carry its own new ST-flip-derived entry, its own SL, and its own targets (§8), so it isn't sharing state with the old leg beyond `parent_trade_id`. For later analysis, the direction label plus `parent_trade_id` are enough to categorise and, if wanted, group a roll-chain's legs back together — no live "continuous P&L" figure is needed at report time.

## 14. ST-15 seed skip-list — excluding known-bad sessions from the daily re-seed window

Since `prometheus.py` is a fresh cron-launched process every session (§3), it never carries an in-memory Supertrend state across days — `seed_st15` recomputes ST_15 from scratch every morning off a rolling `SEED_DAYS=18` calendar-day tail-read (`prometheus_configs.py`). Every single day's regime state depends on that same ~18-day (~13-14 trading-day) window of raw 1-min history, recomputed fresh — so a known-bad session anywhere in that window corrupts the live seed for as long as it stays in the window, not just the one day it happened on.

This is the live-production version of exactly what was just fixed for the backtest: 2026-02-01's MCX Union Budget special session (WTI not trading, thin/disconnected price action) was confirmed this session to distort both raw ST_15 signal flips and SL/target fills, understating the true achievable P&L of both multiplier candidates by real money (₹4,368 at mult 2.0, ₹8,314 at mult 2.5, once fixed). The backtest fix was permanent — drop the date from the historical file, once, forever (`prometheus_backtest/data_loader.py`'s `load_futures_1min`). Live seeding can't do that the same way: the same date keeps re-entering the rolling window every morning for as long as it's within `SEED_DAYS` of today, and a *new* anomalous session (a future Budget day, a muhurat/special session, an exchange-declared correction) could appear at any time, not just retroactively.

**Add `ST_SEED_SKIP_DATES` to `prometheus_configs.py`** (production counterpart of `configs_p3.py`): a plain list of ISO date strings, empty by default, manually populated by an operator when a known-bad session is identified —

```python
ST_SEED_SKIP_DATES = [
    '2026-02-01',  # MCX Union Budget special session, WTI not trading -- added 2026-09-XX
]
```

`seed_st15`/`_tail_read_contract_csv` filters these dates out of the raw 1-min tail-read before resampling to 15-min and computing Supertrend — same mechanism, same place in the pipeline, as the backtest fix. Applies wherever `seed_st15` runs, which includes the rollover re-seed (§6, item 2) as well as the normal daily `_setup()` seed — one function, one fix, no separate handling needed for either caller.

**Same forward-compatibility property as §11's patch, worth naming for the same reason:** the skip-filter operates on the raw 1-min tail-read, upstream of the 15-min resample, not embedded inside it. A future 1h seed function (§17) only needs to consume the *same already-filtered* 1-min series `seed_st15` produces rather than re-implementing its own skip-list pass — provided it's built that way. Flagging now so that's the obvious choice when Phase 4 actually adds it, not something rediscovered the hard way.

**Lifecycle, per direction**: rarely populated, manually pruned, not a permanent growing list. Once a skipped date falls outside the rolling `SEED_DAYS` window (today minus `SEED_DAYS` calendar days > the skipped date), the entry is a no-op — it's excluding a date the window was never going to include anyway — and should be deleted from `configs.py` at that point. `SEED_DAYS=18` calendar days ≈ 13-14 trading days, so roughly 3 weeks after adding an entry it's due for removal. Annotate each entry with the date it was added (as above) so staleness is easy to eyeball rather than tracked separately.

**Recommended, not required**: a non-blocking startup log line (in `seed_st15` or `_setup()`) listing any `ST_SEED_SKIP_DATES` entries that have already aged out of the current window — costs nothing, and turns "did anyone remember to prune this" into something the logs surface on their own rather than relying on an operator's memory.

## 15. Prometheus write-removal — stop writing to the shared MCX contract CSV [DECIDED 2026-09-03]

**The idea.** `data_downloader_mcx.py` was redesigned 2026-09-02 to run once nightly (23:56 IST, right after MCX close) and be the *sole* writer of every contract's on-disk CSV — front-month and next-month, every enabled underlying (`data_pipeline/README.md`). For that to actually hold, Prometheus has to stop writing into the same files during the day: keep its own in-memory intraday 1-min series for its own decision-making, never persist it, and rebuild it from scratch (yesterday off disk, today off a live re-fetch) on every startup — fresh morning start and mid-day crash-restart treated identically, one code path. This removes the write-race the old `_already_up_to_date()` skip existed to avoid (already removed from `data_downloader_mcx.py` — see `data_pipeline/README.md`'s "sequencing note": until *this* section is implemented, Prometheus still writes intraday, so the nightly downloader will redundantly, harmlessly re-fetch CRUDEOIL/CRUDEOILM's session each night).

**Why now, not just "would be nice":** Phase 3 positions span rollovers (§3-§8), and a front-month-only, no-backfill downloader (§8, this session's earlier fix) means the new front-month contract has *zero* history the instant it becomes front-month — unless something tracks it before then. The 2026-09-02 redesign's universal next-month tracking closes that gap from the data-pipeline side. This section is the other half: making Prometheus actually rely on the pipeline as the single source of truth, instead of half-relying on its own historical writes into the same file.

**Every current write into the shared contract CSV, enumerated** (`grep`-verified against `prometheus.py`/`prometheus_functions.py`, 2026-09-02):

| Call site | What it does today | Disposition |
|---|---|---|
| `_merge_1m` (`prometheus.py:530-545`) | Writes every 1-min poll to `_merge_and_save(self._contract['filepath'], new_df)` **and** appends to `self._df_1m_today` in-memory | **Delete the write, keep the in-memory append.** One line removed (`_merge_and_save(...)`); everything downstream (`_handle_new_15m_bar`, called right after) already reads only `self._df_1m_today`/`self._df_15m` in-memory, never the disk file — confirmed by reading it end to end. This is the only change needed to the intraday loop itself. |
| `backfill_contract_if_needed` (`prometheus_functions.py:293-322`) | On a newly-effective contract whose file's oldest row isn't old enough for `SEED_DAYS`, fetches and writes the missing older history | **Keep, as a defensive fallback — orthogonal to this section.** This fixes genuinely-missing *historical* data (an under-tracked contract), not the intraday-poll write point 4 is about. Under the new pipeline design it should rarely fire (front+next month are tracked nightly for every underlying), but if the nightly cron ever fails or the VPS is down, this is the thing that lets Prometheus self-heal instead of silently seeding short. Leave it writing — extending the pipeline's own file when the pipeline itself fell behind is the correct behavior, not a violation of "Prometheus doesn't write intraday data." |
| `backfill_recent_gap_if_needed` (`prometheus_functions.py:325-369`) | Closes the gap between the file's last on-disk row and `now`, sized for downtime *Prometheus's own intraday writes* would otherwise have left | **Dead under the new design — remove the call from `seed_st15`.** Its entire reason to exist was that Prometheus used to be a co-writer of the file's *today* rows, so a restart could leave a same-day hole in them (this is literally the function that fixed the 2026-08-31 Kill Switch incident, minutes 12:03-12:08 lost). Once Prometheus never writes today's rows to disk at all, there is no such hole to close — the file will always end at yesterday's last row, every single day, and the *replacement* mechanism (below) is a different operation, not a repurposing of this one. |

Replace with an unconditional live re-fetch of today 09:00→`now` (see below), which subsumes both the fresh-morning case (an essentially-empty fetch, since `now` ≈ 09:00) and the crash-restart case (the real gap-filler) in one code path. |
| `seed_st15` (`prometheus_functions.py:470-507`) | Tail-reads the file (past days *and* whatever of today it has), resamples, gap-checks, computes ST — treats "the file" as the single source for both | **Restructure, not delete.** Past days stay disk-sourced (now robustly guaranteed by the nightly pipeline instead of best-effort). Today has no disk source anymore under this design — it must come from the new live re-fetch step, concatenated with the disk-sourced past days *before* `_resample_1m_to_15m`/`_find_15m_gaps` run, so gap-checking still sees one contiguous series, not two independently-validated halves. |

**The new startup sequence** (`_setup`/`seed_st15`, both a fresh 09:00 start and a mid-day crash-restart, same code path):
1. `backfill_contract_if_needed` — defensive, as above, rarely fires.
2. Tail-read the shared file for calendar days *before* today only (an explicit cutoff, not "whatever's on the file" — the file may contain nothing for today, or, during the transition described in the sequencing note above, it may still contain some of today's rows from an old build; excluding today explicitly avoids depending on which is true).
3. Fetch today `SESSION_START_TIME`→`now` live from the broker (same `fetch_one_minute_window`/resilient-poller mechanics §4 already built, reused — not new infrastructure), building `self._df_1m_today` from scratch every single startup regardless of restart vs. fresh start.
4. Concatenate (2) and (3) into one 1-min series, *then* resample to 15-min, gap-check, compute ST — same `_resample_1m_to_15m`/`_find_15m_gaps`/`compute_st` functions, unchanged, fed a differently-assembled input.

**Two incident-derived constraints this must not lose, both already enforced by existing code and unaffected by the restructuring above — call this out explicitly when it's built, don't just assume it carries over:**
- `_resample_1m_to_15m`'s "a window only counts once it has genuinely finished elapsing by `now`" guard (2026-08-31, 12:13:49 restart produced ST=8105.67 from a 13-of-15-minute partial bar vs. the chart's correct 8102.33). Applies identically to a bar built from step 3's live-fetched today data — the function itself doesn't change, but it's now doing more of the work (all of today, not just whatever gap remained), so it deserves being named as still-load-bearing, not silently assumed.
- The *intent* behind `backfill_recent_gap_if_needed` (never let a same-day hole go unrecovered) doesn't disappear — it moves entirely into step 3 above (an unconditional full re-fetch, not a diff against a stale on-disk marker). This is a strictly simpler mechanism than the old gap-diff approach, but it changes the failure mode described next.

**New robustness trade-off this introduces, and the startup retry decided to cover it.** Today's data now has no on-disk fallback. Old design: if a live poll failed, whatever had already been written to disk for today survived a restart untouched, and only the actual gap needed re-fetching. New design: a broker/network hiccup during step 3's re-fetch blocks `seed_st15` entirely for the *whole* day so far, not just the failed window — `_find_15m_gaps` still refuses to seed on any hole, and there's no cached partial copy to fall back to. Verified how costly this actually is: `_setup()` calls `seed_st15` exactly once (`prometheus.py:218-222`) and returns `False` on any failure, which `run()` treats as "Setup failed" — no retry, no trading for the rest of the day, on a single-shot basis.

**Decided: wrap `_setup()`'s `seed_st15` call in a bounded startup retry** — up to 5 attempts, 2 minutes apart (~10 minutes total before giving up), each attempt re-running the full `seed_st15` sequence from scratch so it naturally picks up wherever the broker/network has recovered by then. This is a blocking wait, deliberately, unlike every other retry loop in this plan — and that's fine specifically *here*: `_setup()` runs before the main loop starts, before any position exists and before `_check_exit_conditions_ltp` has anything to monitor, so there's no concurrent exit-check loop to starve the way §4/§7/§12's non-blocking designs exist to protect. Log every failed attempt; Slack a WARNING-level heads-up on the first failure (visibility that something's off, without alarm), escalate to CRITICAL only if all 5 attempts are exhausted — matching the debounced-escalation shape already used in §7's `_pending_flip` and the existing stale-tick watchdog, rather than paging on every attempt. Rationale, per user direction: this plan's whole point is to make automated recovery the norm and human intervention the rare last resort — a single-shot startup failure on what's likely a transient few-minute network blip (the same class of failure §12 already established as typically self-resolving within about a minute) doesn't meet that bar.

**Status: decided, not yet built.** Confirm the sequence above before touching `prometheus.py`/`prometheus_functions.py` — this is live-trading crash-recovery code, not yet live-tested even under `DRY_RUN=True`, and CLAUDE.md's Production QC rule (read the entry path end-to-end before any live session) applies with extra weight here given how much of this section is incident-derived from real 2026-08-31 failures.

*Correction to an earlier pass of this audit: §7 is not fully unaffected.* First pass claimed Rule 7's combined order is entirely downstream of "an entry decision was made" and agnostic to what made it — true for the retry/ghost-recovery/tie-break *mechanics*, but wrong about **sizing**. §7's combined order computes `old_open_lots + new_trade_lots` *once, up front*, on the premise a flip is always exit-and-entry together. Once a filter can block just the entry half, that's not a downstream call-skip, it's the order's own requested quantity changing — `new_trade_lots` must be computed as its own explicit step (zero when blocked), not assumed. §7 now documents this as a third degenerate case, symmetric to its existing "both lots flat → entry-only" one. Nothing to build in Phase 3 (the gate doesn't exist yet), but the sizing logic needs to be shaped this way from the start so Phase 4 has one place to hang the filter, not a restructure.
