**§8 implementation notes (2026-08-08):** Before wiring Path A into production, the ST_5/ST_15 output was verified bar-for-bar against the live chart from 2026-08-03 onward (`research/iris_st_verification/`) — matched to the decimal except 3 flip-bar values (drift of 1.5-11 points), which trace to Supertrend's known "dormant band" property: the inactive band recomputes from ATR every bar with no reality-check, so it can silently differ until the next flip exposes it. Confirmed not a warmup-length artifact (identical result seeding from 6 weeks vs. the full 7-year history) and confirmed self-correcting (one case converged from an 11-point gap to ~0.05 within a trading day, via a monotonic sequence of 18 ratchet events). Flip *timing* never diverged in anything checked. Root cause of the initial cold-start value gap itself (why our fresh flip-bar value differs from the chart's) remains unexplained — accepted as expected Supertrend behavior rather than chased further.

**§1 implementation notes (2026-08-08):** Apollo's retry/backfill pattern (outer 5x retry, 10s apart, persistent missed-candle queue) required one deliberate deviation, not a straight port: Apollo's retry sleeps block its main loop, which is safe for Apollo since nothing else needs to run during that wait. Iris's in-trade exit monitoring runs every 0.5-1s and must never freeze while a position is open, so the retry is non-blocking — a `_next_candle_retry_at` timestamp gates the next real attempt while the main loop keeps ticking (exit checks, Slack commands) every cycle regardless.

**§4/§6/§7 implementation notes (2026-08-08):** Split §4 into two pieces rather than a straight Apollo port. The reporting half (startup Slack message with seeded 5m trend + 15m regime, matching Apollo's seed-completion message) shipped as-is. The missed-flip-recovery half is NOT a port of Apollo's `get_last_completed_flip()` — Apollo auto-*enters* if the window's still open; user explicitly chose alert-only for Iris (`_check_missed_flip_at_startup`), since a flip discovered after an unknown restart delay means entering partway into a move on a strategy built around a short, controlled hold time. §6 added dedicated Slack alerts for both the 5m flip and 15m regime flip, independent of any resulting trade action, routed to `SLACK_TRADEBOT_CHANNEL` (the open question on channel choice — no existing channel convention cleanly fits a pure informational ping — resolved this way, not yet explicitly re-confirmed with the user). §7 added ST_15's current value to every 5m cycle's log line (previously only visible on the 15m boundary bars); CSV persistence was already covered by §8.

**Live incident (2026-08-10) — Path B silent failure on mid-session restart, fixed:** first live day under the rebuilt pipeline went cleanly (seeding matched the chart exactly, entry/exit/exit-by-max-hold all correct), but a manual restart at 10:43 (Slack Kill Switch, then fresh start) exposed a real gap. `_build_today_5m`'s only resilience was `fetch_candles`'s inner 3-attempt/1s burst — no retry beyond that. AngelOne's rate limit hit all 3 attempts, `_build_today_5m` silently returned empty, and `seed_st` proceeded with Path A only: seeded 5m trend read *bearish* (Friday's close) when the real 5m trend had flipped bullish 23 minutes earlier at 10:20. Self-corrected on the very next live candle (~2 minutes later, 10:45) with no trade entered in the gap, so no financial impact this time — but the exposure was real: a genuine flip firing in that ~2-minute window would have been evaluated against a wrong regime. This is a resilience *regression* introduced by §8 itself: the old pre-§8 `seed_st` did a single live fetch covering both past and today in one call, and failing it entirely made `_setup()` return False — loud and obvious. Splitting into Path A (disk, always succeeds) + Path B (live, can silently fail) traded a loud failure for a silent one. Fixed by (1) giving `_build_today_5m` its own `CANDLE_FETCH_RETRIES`/`CANDLE_FETCH_RETRY_INTERVAL` retry loop beyond the inner burst — blocking is fine here since this runs once at startup, not inside the live loop — and (2) an explicit check in `_setup()` that fires a Slack alert if the seed still has zero today-rows despite the market having been open long enough that it shouldn't. Both verified with isolated tests (retry-then-succeed, retry-then-give-up-cleanly, alert-fires-only-when-warranted).

**Candle-poll jitter — tried and reverted (2026-08-10):** added `CANDLE_POLL_JITTER_MS=200`, a small delay before the first poll at each 5-min boundary, to test whether polling at the exact clock tick collides with every other bot on the broker (the "exceeding access rate" hits are on a single request every 5 minutes, well under any documented limit). Reverted same day per user instruction before gathering enough data to judge the hypothesis either way — the 200ms delay, compounded with the run loop's own ~1s tick granularity, was pushing the actual candle update further from the boundary than intended (observed ~2s instead of the ~1s it was taking before), which wasn't the tradeoff wanted. The underlying "why does a single request every 5 minutes get rate-limited at all" question remains open and unexplained.

## 0. Why this exists — today's incident

Analysis of `iris_production/logs/iris_20260807.log`, full session: 09:15:09 start to 14:21:52 stop (Slack Kill Switch, triggered manually once the pattern below was found — clean shutdown, "Dropping control immediately", no stuck state, no open position at the time):

- No trades entered all session. Not a bug — the 5-min trend stayed `bearish` the entire day with zero fresh 5m flips; the only regime event was the 15-min regime catching up to `bearish` at 11:15:02. Since `ST_FAST` needs an actual crossing (`trend != trend.shift(1)` in `compute_st`) to fire, a trend that never left `bearish` in the first place could never produce one — confirmed there was no signal being missed by stopping early.
- **69 `getCandleData` rate-limit warnings** (`Access denied because of exceeding access rate`) across the session — 13 instances where all 3 retries were exhausted.
- **9 of 61 expected 5-minute bars (15%) never appear in the log at all**: 09:55, 10:15, 10:25, 10:30, 10:55, 11:00, 12:15, 12:55, 13:30.
- Traced to the code, not just correlation: `_fetch_candle()` (`iris.py:358-376`) fetches a narrow 3-bar window and extracts exactly one candle. `_update_5m_st()` (`iris.py:378-390`) appends that single row to the running `self._df_5m` series. When `fetch_candles` exhausts its 3 retries and returns nothing, the cycle is skipped and **that candle is gone permanently** — the next successful cycle only fetches its own new candle, it never backfills. If a genuine flip had occurred inside one of those 9 gaps, it would have been structurally undetectable, not just delayed — today's monotonic trend means this probably didn't cost anything, but that's luck, not a property of the system. The missing-bar rate held steady (~15-17%) across the whole session rather than worsening over time.
- This is a recurrence of an already-documented AngelOne behavior, not a new mystery — `plans/closing-auction-session.md` §7.4 recorded the same symptom during the CAS investigation: "AngelOne's historical-candle endpoint hit a sustained, undocumented throttle... well under the documented 3/sec-180/min-5000/hour limits."
- **Note for §5**: this log stops at 14:21, well before the 15:15-15:25 CAS auction window even opens. It cannot answer §5 on its own — that still needs a direct post-close `getCandleData` pull for that specific window, since Iris was never live-polling during it today.

This prompted a systematic comparison against `apollo_production/`, which handles an analogous problem (Nifty-index candle fetching + Supertrend signal generation) and has significantly more live-trading history. Every item below is a concrete gap found by reading both codebases side by side, not a general impression.

## 1. Candle-fetch retry/backoff resilience

**Apollo** (`apollo.py:334-407`, `apollo_configs.py:159-160`): inner 3-attempt burst (same as Iris) via `_fetch_latest_candle`, but if that fails entirely, escalates to an outer loop — `CANDLE_FETCH_RETRIES = 5` more attempts, `CANDLE_FETCH_RETRY_INTERVAL = 10` seconds apart (up to 18 total attempts over 50+ seconds). Calls `_reset_counters()` before each outer retry — actively resets client-side rate-limit counters rather than retrying into the same throttle window. If still unrecovered, the timestamp goes into a persistent `self._missed_candle_ts_list`, which is actively retried on *every subsequent loop iteration* (not abandoned), and when recovered, the candle is backfilled into the ST series in correct chronological order before the current bar is processed.

**Iris** (`iris_functions.py` → `fetch_candles`): 3 attempts, 1 second apart, then permanently gives up. No counter reset. No backfill queue — `_fetch_candle` returning `None` just skips that cycle forever.

**Recommended:** port Apollo's exact pattern — outer retry loop with counter reset, persistent missed-timestamp queue retried each loop iteration, chronological backfill into `self._df_5m` (and `self._df_15m` where relevant) before processing the current bar.

## 2. 75-min/15-min resampling consistency

**Apollo**: 75-min timeframe is *always* derived by resampling the already-fetched 15-min dataframe (`_compute_75min_st`, `supertrend.py:304`) — zero extra API calls, ever. Necessary in Apollo's case since AngelOne's `getCandleData` has no native 75-min interval.

**Iris**: resamples 5m→15m correctly at seed time (`_resample_to_15m`, `iris_functions.py:142`, used in `seed_st`) — but the live loop doesn't reuse that pattern. `_update_15m_regime()` (`iris.py:407-408`) calls `_fetch_candle(close_ts, REGIME_TF_MIN)`, which sets `interval = 'FIFTEEN_MINUTE'` and makes a **separate, independent API call** every 15 minutes, on top of the `FIVE_MINUTE` call already happening every 5 minutes. Inconsistent with Iris's own seed-time logic, and roughly a third more `getCandleData` traffic than necessary — a direct contributor to today's rate-limit exhaustion.

**Recommended:** make the live loop resample the 15-min regime from `self._df_5m` the same way `seed_st` does, and drop the separate `FIFTEEN_MINUTE` fetch entirely. Confirmed still correct as originally stated, after §5/§8 — this is specifically about *today's* live 15-min regime, which stays on the 5-min-polled series (§8's "Path B"); the 1-min reconstruction from §5 only applies to seeding past days (§8's "Path A") and doesn't change this recommendation at all.

## 3. On-disk ST cache persistence

**Apollo**: `data/supertrend_cache.csv` (`apollo_configs.py:24`, `_save_st_cache`, `supertrend.py:367-378`), overwritten after every candle close — 15-min OHLC + Supertrend + trend + trend_flip, trimmed to `ST_HISTORY_CANDLES`. Serves both intra-session restart recovery and as a durable, inspectable record.

**Iris**: no cache file at all. No restart recovery without re-seeding from the API, and no way to examine the running signal history except parsing the log file after the fact — exactly what today's whole investigation required.

**Recommended (concretized per item 7 below):** add an equivalent CSV, written after every 5-min *and* 15-min update, holding OHLC + ST_5 + trend_5 + flip_5 + ST_15 + trend_15 + flip_15 per row.

## 4. Slack reporting granularity — general

Neither strategy pings Slack for a "pure" regime flip independent of a resulting trade action currently — flips feed into entry/exit logic, which has its own alerts. Two concrete gaps found on Iris's side specifically:

- Apollo's seed-completion Slack message reports the initial regime state ("*Apollo*: Supertrend seeded (N candles). 75-min trend: bullish/bearish.", `apollo.py:159-161`). Iris's startup message (`iris.py:206-208`) is generic — strategy name + lot count — and doesn't report the initial 5m/15m regime at all.
- Apollo has a **missed-flip-recovery mechanism** at startup (`get_last_completed_flip()`, `supertrend.py:195-213`; used in `apollo.py` around line 550-576): if a flip happened earlier today before Apollo started/restarted and the entry window is still open, it detects this, alerts Slack ("*Apollo*: Missed flip detected at HH:MM..."), and can still act on it. **Iris has no equivalent at all** (confirmed — zero matches for `missed.flip`/`get_last_completed_flip`/`recover` in `iris.py`/`iris_functions.py`). A restart mid-session silently loses any flip that occurred while Iris was down — no detection, no alert, no recovery.

**Recommended:** add regime state to Iris's startup Slack message; port Apollo's missed-flip-recovery mechanism (5m and/or 15m, to be decided).

## 5. Live 5-min/1-min candle integrity during the CAS window — ANSWERED

Investigated post-close 2026-08-07 via a live, single-login AngelOne research session (Iris fully stopped, no rate-limit contention). Pulled raw, uncorrected `getCandleData` for both 2026-08-07 and 2026-08-06, at both `ONE_MINUTE` and `FIVE_MINUTE` intervals, 15:00-15:40 each day, then cross-checked against what AngelOne's own chart displays for the same window and against `data/cas_auction_tracking.csv`.

**What the raw API actually returns (both days, same shape, verified against the actual saved CSVs, not just eyeballed):** continuous real 1-min ticks through 15:14. A single flat row at 15:15 — O=H=L=C all equal, and *not* equal to 15:14's own close, confirming this is the exchange's published VWAP(15:00-15:15) reference price, not a stale-LTP artifact. Then a complete void — zero rows at any granularity — for 12-13 minutes. Then a single flat row at the terminal print (15:29 on 08-07, 15:28 on 08-06). **Nothing else at all after that row — confirmed by row count, not inference: yesterday's saved 1-min CSV has exactly 17 data rows, the last one timestamped 15:28.** The raw feed simply stops; it does not contain a 15:29 row on the day the terminal print landed at 15:28.

**What the chart shows for the same window, which differs from the raw API in two places, not one.** First (already covered above): the candle where the terminal print lands is reconstructed on the chart, not flat — open equals the carried-forward pre-auction reference value, close is the print, high/low direction-aware. Second, and this is the correction from this review: **the chart also displays a fixed cutoff at 15:29 regardless of when the transition candle itself landed.** On 08-07 the transition *was* 15:29, so there's nothing further to show. On 08-06 the transition was 15:28, and the chart still shows one more candle at 15:29 — flat, at the transition's close (24636) — even though **that row does not exist anywhere in the raw API response** (confirmed above: 17 rows, stops at 15:28). This second piece is pure chart-side (or equivalently, our own backfill-side) synthesis; it is not something a passive "resample whatever the API returns" approach will ever produce, because the underlying row simply isn't there to resample from.

**Resampling confirms it's clean once the 1-min series is correctly reconstructed:** 5-min and 15-min chart views for both days are consistent with straightforward OHLC aggregation *of the chart's own corrected-and-extended 1-min series* — e.g. 08-07's 5-min "15:25" bucket (spanning 15:25-15:30) shows open=24557/close=24570.65, exactly what aggregating [flat,flat,flat,flat,transition-candle] produces. Once that 1-min series is correct and complete, the resampler needs zero special-case knowledge of which row was the transition candle or where the auction gap was — it's pure fixed-clock-time-bucket OHLC aggregation over whatever rows exist. All of the transition-candle-awareness belongs in reconstruction (§8/§9), not in resampling.

**The fixed cutoff, precisely stated:** the day's reconstructed 1-min series should run through **15:29** — the transition candle if it lands there or earlier (with flat filler candles synthesized, not assumed present in the raw feed, for every minute between the transition and 15:29 inclusive), full stop otherwise. It does not extend to 15:39 the way the historical pipeline's `extend_to_day_close` output does for a different purpose (see §9) — feeding those extra flat candles into `compute_st` would add contentless bars the real chart's ST never sees. **Open item, not yet verified with data:** both examples here have the terminal print landing at or before 15:29. Whether 15:29 is a truly fixed cutoff or would instead track a later print (CAS docs say the print can land anywhere 15:16-15:35) is unconfirmed — only relevant if a day surfaces where the print lands after 15:29.

Full implementation design is in §8 (Iris) and §9 (data pipeline, separate codebase, flagged distinctly per the user's request).

## 8. Iris — rebuild the 1-min reconstruction and seeding around a persistent CSV

Supersedes §2's original resampling recommendation now that §5 is answered. This is the actual fix for the CAS-window blind spot, and it subsumes §3/§7's cache-persistence goal rather than sitting alongside it as a separate feature.

**Clarified on review: this is two separate data paths, not one, and the 1-min reconstruction only applies to one of them.** Earlier wording in this section (and in §2) risked being read as "switch live polling to 1-min and resample everything from that," which is not the design — live polling stays at 5-min cadence throughout; sending 5x the requests by polling every minute would make §0/§1's rate-limit problem worse, not better. The two paths:

**Path A — seeding from past (fully closed) days.** Every day strictly before today, in whatever lookback window `ST_PERIOD`-based warmup needs, is seeded by pulling 1-min history for those days, applying the reconstruction below once at 1-min granularity, and resampling *up* to both 5-min and 15-min from that single corrected series. Reconstruction logic (the chart-matching rules from §5):
1. Real ticks pass through unchanged.
2. Any absent minute *before* the terminal print gets flat-filled forward at the last known reference value (the pre-auction VWAP print).
3. The candle where the terminal print lands is reconstructed, not taken as-is from the API: open = the carried-forward flat value, close = the new print, high/low = max/min of the two (direction-aware — CAS can push the print either above or below the pre-auction reference).
4. If the terminal print lands before 15:29, synthesize additional flat candles (at the print's value) for every minute from the transition through 15:29 inclusive — confirmed necessary by checking actual raw data, not assumed: 2026-08-06's raw feed has no row at all for 15:29 (17 rows, stops at 15:28) even though the chart shows one.
5. The reconstructed series stops at 15:29 — no flat-extension out to 15:39 (that's §9's data-pipeline-only concern, for a different purpose, and must not leak into what Iris computes ST on).

This is a *seeding-time-only* concern. It applies once per historical day, not continuously — today never needs this path, because at any normal seed time (market open, or a same-day restart) today hasn't reached its own CAS window yet, and by the time it does (15:15+), Iris's `MAX_ENTRY_TIME=15:00`/`EXIT_BY_TIME=15:15` mean today's own trading decisions never depend on data from that window anyway. The correctness only matters once today becomes a *past* day for tomorrow's seed.

**Path B — today, whether from a fresh 09:15 start or a same-day restart.** Unchanged from §2's original recommendation, now reconfirmed: poll 5-min candles at the existing 5-minute cadence (no change to polling frequency), and at each 15-minute boundary resample ST_15 from the three most recently polled 5-min candles already in hand — no separate `FIFTEEN_MINUTE` API call, matching what §2 already flagged as redundant. On a same-day restart, today's already-elapsed candles are recovered the same way — a poll for today's 5-min candles from market open to now, then resampled to 15m — never via the 1-min/reconstruction path in Path A. Today's own candle series is never built from 1-min data, full stop.

**Persistence (both paths feed the same on-disk series):**
- Path A's resampled-from-1-min history for past days, plus Path B's live-polled 5-min candles for today, together form the running series persisted to CSV — this is where §3/§7's cache-persistence goal is actually satisfied, as a byproduct of needing a durable record anyway, not a bolt-on.
- Always delete and rebuild this CSV fresh at the start of a new day or on any Iris restart — no cross-restart reuse of a stale cache (deliberately simpler/more conservative than Apollo's restart-recovery-from-cache approach, given everything found in §0/§1 about how easily the live incremental path accumulates silent corruption; reseeding fresh sidesteps that risk rather than trying to detect and repair it after the fact). "Rebuild fresh" means re-running Path A for past days and Path B for today's elapsed portion, every time — not literally re-fetching things that haven't changed if that turns out to be wasteful in practice, but no trusting of an old file's contents across a restart boundary.

**Seed size — verified sufficient, not a concern.** Checked candle counts against actual local data before assuming Path A's window is adequate: Apollo seeds exactly 600 15-min candles (`ST_HISTORY_CANDLES`, 24 trading days) for ST_15, ~120 75-min candles for ST_75; Iris currently seeds ~755 5-min candles (`SEED_DAYS=13`, 10 trading days) for ST_5, ~251 15-min candles for ST_15. With `ST_PERIOD=10` for all of these, the EMA weight remaining on the earliest seeded candle is `(1-1/period)^n` — even the thinnest of the four (Apollo's ST_75, 120 candles = 12x period) decays to `3.2e-06`, and Iris's own numbers are more converged than Apollo's (ST_5 at 75.5x period, ST_15 at 25.1x period), both far past the standard ~10x-period "fully converged" threshold (`~2.7e-05`). No accuracy gap to close here. Worth noting for the record: `SEED_DAYS=13` was originally sized to stay under AngelOne's live per-request record cap ("13d × 75 bars/day = ~975 bars (<1000 API limit)", `iris_configs.py`) — an API-request-size constraint, not an ST-accuracy one. Once Path A reads from disk instead of a live pull, that constraint no longer applies; the window could be widened for other reasons without any accuracy justification needed, but there's no accuracy reason to.

**Daily computing load — measured, not a concern.** Path A runs once per day before the 09:20 first poll/signal check, so the real question is cost against that ~5-minute (300s) budget, not absolute speed. Timed against real local data: reconstruction + resampling to 5m/15m + the actual `SupertrendIndicator.calculate()` loop for both timeframes combined — **41ms**. The only cost that showed up as non-trivial was reading the historical source file: a naive full `pd.read_csv` of the entire multi-year `nifty.csv` (696,767 rows) took **6.5 seconds** just to then filter down to the last 13 days — 99%+ of that read is wasted work. Fixed by tailing instead of reading the whole file: shell `tail -n 6000` (a comfortably oversized constant — 13 calendar days only needs ~3,500-3,850 rows once weekends are excluded, 6000 leaves real headroom for a few milliseconds of cost) plus `head -1` for the column header, then parse only that slice and apply the same date filter as before. Measured: 2.8ms (shell) + 91ms (pandas parse of 6,000 rows) = **93.7ms total, a 68x speedup**, and it covered 21 calendar days in the test run — more margin than needed. **Full Path A pipeline, tail-based: ~130-150ms, against a 300,000ms budget.** Not remotely a concern; noted here mainly so the tail-based read (not a naive full-file read) is the one that actually gets implemented.

**Interaction with §1:** the retry/backoff hardening in §1 still matters for the *normal-hours* rate-limit problem (§0's incident), but does nothing for the CAS-window gap specifically — retrying an exact-timestamp query against a timestamp that will never have data just fails the same way every time (already established in the §5 discussion prior to the raw-pull investigation). §1 and §8 are both needed; they fix different failure modes.

## 9. data_pipeline — CAS gap-fill correction (separate codebase, flagged distinctly)

Same root cause as §5/§8, different repo area (`data_pipeline/data_downloader_angelone.py`), affecting historical/backtest data rather than Iris's live signal — kept as its own item since it's a different codebase with different consumers (any backtest reading `nifty.csv`/`sensex.csv` through a CAS-era day, not just Iris).

**The bug:** `fill_missing_candles`'s current design deliberately leaves the terminal auction print's own OHLC untouched, reasoning (per its own docstring) that forcing its open to the pre-auction close "would produce an invalid candle." §5's chart evidence shows this reasoning doesn't hold — the chart's own transition candle *does* exactly that (open = carried-forward pre-auction value, close = terminal print, high/low direction-aware), and it's a normal, valid OHLC candle, not an invalid one. The pipeline has been producing a flat terminal-print candle where the real chart shows a candle with genuine range, for every CAS-era day since 2026-08-03.

**Three concrete fixes needed:**
1. Fix `fill_missing_candles` itself to reconstruct the transition candle per §5's rule, going forward.
2. **Backfill/correct the existing `nifty.csv` and `sensex.csv`** for every already-downloaded CAS-era day (2026-08-03 onward) — this is retroactive data correction, not just a forward-looking fix, since the CAS-force-close Artemis backtest work from a few days ago (and any other backtest touching this data) consumed the uncorrected version.
3. **Verify (not yet confirmed) whether fix 1 alone is sufficient, or whether `extend_to_day_close` also needs a change.** Unlike Iris's live path (§8, step 4), the data pipeline already has a mechanism that extends flat candles from "whatever the last real row is" through 15:39 — which, if the last real row is fix 1's corrected transition candle, would produce a correct 15:29 row (and everything after) as a side effect of the existing 15:39 extension, with no new code needed for that specific gap. This is a reasonable read of the current code but hasn't been traced end-to-end against the actual gap-detection window (`CAS_GAP_MAX_MINUTES`) to confirm the 15:15-to-transition gap is reliably detected as one contiguous CAS gap in every case — needs an actual test run against a corrected day (e.g. 2026-08-06) before assuming fix 1 is the whole fix.

**Explicitly not the same fix as §8** — §9's flat-extension through 15:39 is correct and necessary for the data pipeline's own purpose (matching the extended derivatives session, row-count alignment for downstream consumers). §8 explicitly does *not* want that extension for Iris's ST calculation. Both are correct simultaneously, for different consumers of the same underlying event.
